## 2. Six places the documentation overruled the brief

Precedence per `docs/32`: T0 > T1 > T2 > T3 > T4.

### 2.1 The path scheme is staging-then-move, not `incident-evidence/{userId}/{incidentId}/`

brief §14 proposes:

```
incident-evidence/{userId}/{incidentId}/{evidenceId}
```

`docs/15 §3.1` is **normative** and specifies four legal shapes:

```
staging/{uid}/{mediaId}.{ext}                                    ← client PUT
incidents/{incidentId}/reports/{reportId}/{mediaId}.{ext}         ← final
incidents/{incidentId}/supplements/{reportId}/{mediaId}.{ext}
quarantine/{mediaId}.{ext}
```

`docs/15 §3.2` gives the reason and it is load-bearing:

> **The incident ID does not exist at upload time.**

The report flow is *pick a photo → upload it → then submit the report*. When a citizen taps "upload photo" there is no `incidentId` and no `reportId`; both are Firestore auto-IDs created later inside the `POST /api/incidents` transaction. brief §14's structure is not merely different, it is **unsatisfiable** at the moment it is needed. Its own heading says "Recommended **conceptual** structure".

The brief's security intent is fully honoured, and more strictly: the client never contributes a single character to the path.

### 2.2 Transcription is a by-product of the triage call — there is no separate STT step

brief §18 specifies a two-pass pipeline (`Voice → SpeechToTextService → Transcript → Gemini Triage`).

**`docs/09` is a T0 anchor and specifies one pass.** `docs/09 §5` lists `audio_transcript` and `audio_transcript_uncertain` as fields 16 and 17 of the *same* output schema, and `§6` gives the prompt an `## AUDIO` section: *"If audio is provided, transcribe it faithfully in its original language."* `docs/27` N7 confirms: `MediaRecorder → audio evidence → Gemini transcription`.

Phase 4 already implemented this: `services/ai/prompts.ts` has the `## AUDIO` section, `services/ai/rules.ts` reads `output.audio_transcript`, `services/ai/schema.ts` validates it.

brief §3 anticipates exactly this and provides the escape hatch:

> "…unless the project's Gemini architecture explicitly supports direct audio analysis."

It does. So `SpeechToTextService` abstracts the **result**, not a second model call:

| Design | Rejected because |
| --- | --- |
| Dedicated STT call before triage | A **second Gemini implementation** (brief §21 forbids), a second prompt to keep in sync, a second failure mode, a second quota cost — to compute a field the triage call already returns. |
| Third-party STT (Whisper, Deepgram) | brief §18: "do NOT invent an expensive service." Not configured; a budget decision, not this phase's. |
| Browser `SpeechRecognition` | Chrome-only, non-deterministic, and a **second source of truth** that can disagree with the transcript Gemini reports. |

### 2.3 The maximum recording is 120 s, not the brief's example of 60

brief §6 gives 60 s as an example, then says "If the project specification defines another maximum, follow that instead." `docs/15 §7.1` and `config/limits.ts` both say **120** (FR-006). The number lives in exactly one place — `getUploadLimits().maxAudioDurationSec` — so the client's auto-stop and the server's cap cannot disagree.

### 2.4 `MediaRef` has no `downloadUrl`

brief §16's example shape includes `downloadUrl?: string`. **It is deliberately absent.**

A Firebase download URL is a long-lived bearer token. Persisting one in a Firestore document readable by anyone who can read the incident means the URL outlives the authorization decision that produced it. `docs/15 §12` specifies a 15-minute signed URL minted on demand, after the `§13` access matrix is evaluated. brief §30 itself warns against exposing "private download tokens".

A security check enforces the omission, so removing the decision is deliberate rather than accidental.

### 2.5 `swipe`-free capability detection, and five permission outcomes not two

brief §7 names five states (granted, denied, dismissed, unsupported, unavailable). `classifyPermissionError` maps every `DOMException` name to one of five outcomes. The two that matter most:

- **`NotAllowedError` on an insecure context is reported as `insecure`, not `denied`.** The permission was never asked for. Telling a citizen "you denied microphone access" when the page was `http://192.168.1.5` is a false statement about their own actions, and the fixes are completely different.
- **An unrecognised error is `unavailable`, not `denied`.** Attributing a failure to the user's refusal when we do not know that is the accusation this classification exists to avoid.

### 2.6 `r01_createIncident`, not a new capability

The 61-row matrix in `docs/22` is not extended. Evidence upload is not a separable privilege: adding `r62_uploadEvidence` would permit granting upload without `r01_createIncident` — a user who may fill the bucket but never file a report. Not a distinction this product has any use for.

## 3. The seven bugs this phase's own tests found

All seven were in newly written code, and all seven are documented in the source at the point of the fix.

### 3.1 The path regexes had no capture groups — **every upload would have been silently dropped**

The highest-severity bug in the phase.

```ts
// shipped
`^staging/[A-Za-z0-9_-]{1,128}/med_[A-Z2-7]{12}\\.(${EXT_ALTERNATION})$`
// correct
`^staging/([A-Za-z0-9_-]{1,128})/(med_[A-Z2-7]{12})\\.(${EXT_ALTERNATION})$`
```

`validateMediaPath` destructures `exec()`'s capture groups rather than re-parsing. With no groups, `uid` was `undefined`, `undefined !== callerUid` was always true, and **the function returned `null` for every possible input**. The regex matched correctly the whole time.

**A `.test()`-based test would have passed throughout.** `tests/unit/uploads/paths.test.ts` therefore asserts on the *return value* of `validateMediaPath` for known-good paths. This is now security check #1, which counts capture groups.

A second, related bug: the `med_` prefix sat *outside* the group, so the returned `mediaId` was `ABCDEFGH2345` rather than `med_ABCDEFGH2345` — making every `releaseClaim` a silent no-op.

### 3.2 `generateMediaId` emitted 32 body characters where the regex demands 12

```ts
const bytes = randomBytes(MEDIA_ID_ALPHABET.length);  // 32 — the ALPHABET's length
for (let i = 0; i < MEDIA_ID_ALPHABET.length; i += 1) // 32 iterations
```

`MEDIA_ID_BODY_LENGTH` is 12. The two numbers are 32 and 12 and nothing about the expression distinguishes them. **Every id the server minted failed its own `MEDIA_ID_RE`**, so every signed URL pointed at a path Storage would refuse. The test that caught it is a closed loop: generate with the real generator, assert against the real regex.

Phase 4's lesson applied — an assertion helper that re-derives its constant from the same private value proves nothing, so `MEDIA_ID_ALPHABET` is exported for exactly this test.

### 3.3 The 120-second cap would never have fired

```ts
React.useEffect(() => {
  const timer = setTimeout(() => stop(true), maxSeconds * 1000);
  return () => clearTimeout(timer);
}, [state, maxSeconds, stop]);   // ← `stop` closes over mimeType and onRecorded
```

`stop` has a new identity every render, and the elapsed ticker re-renders four times a second. The timer was therefore cleared and recreated 4×/second, so **the cap never triggered and recording was unbounded** — the exact failure brief §6 exists to prevent. Invisible until someone records for two minutes.

Fixed with a stable `stopRef`, so the timer holds a fixed identity while calling the current closure.

### 3.4 A factual error about RFC 4648 base32

A comment claimed the alphabet excludes `0/1/8/9/I/L/O`. It excludes only `0, 1, 8, 9`; `I`, `L` and `O` **are** symbols. Harmless in code, but a "human-friendly alphabet" rationale built on a false claim is worse than the ambiguity it claims to prevent. Corrected in place, with the correction recorded.

### 3.5 `signedReadUrl` took a `mimeType` it then ignored

The doc comment argued that re-specifying the content type would create a second place for two things to disagree — and then the function took the parameter and did `void mimeType`. The argument and the signature contradicted each other. Resolved the way the argument says: parameter removed. (ESLint surfaced this; the fix was a design correction, not a lint suppression.)

### 3.6 `byteCapFor` returned the image cap for audio

`return uploadConfig().maxImageBytes` regardless of `contentType` — a 15 MB audio clip would be capped at 5 MB. It was also unused, and duplicated a value `ALLOWED_MEDIA` already owns. **Removed rather than fixed**: the correct value has exactly one home, and `signUpload` already applies `Math.min(tableCap, envCap)` correctly.

### 3.7 `video: false` nested inside the `audio` constraints

```ts
audio: { echoCancellation: true, noiseSuppression: true, video: false }  // TS error
```

`video` belongs to `MediaStreamConstraints`, not `MediaTrackConstraints`. Nested, it is both a type error and a silently-ignored field.

## 4. One bug the security checks found in themselves

Worth recording because it is the project's stated A/B rule paying off.

Check #4 originally asserted the dangerous-signature loop runs before the media checks via:

```js
sniffSource.indexOf('for (const [label, signature] of DANGEROUS_SIGNATURES)') <
  sniffSource.indexOf('jpegLooksReal(buf)')
```

Mutation testing showed that **deleting the loop entirely made the check pass** — `indexOf` returns `-1` when absent, and `-1 < anything` is `true`. A "is A before B" assertion on two strings that does not also assert existence is asserting a tautology. Fixed to require both indices be found *and* ordered.

## 5. The sniffer

`services/uploads/sniff.ts` — pure, no network, no clock, no randomness. The only place bytes are turned into a type claim.

**Order is the security property:**

1. **Dangerous signatures first** (PE, ELF, Mach-O, shebang, ZIP, RAR, 7z, gzip, bzip2, xz). A polyglot is defined by its first bytes; a file whose header is `PK\x03\x04` is a ZIP regardless of what follows. A ZIP renamed `.jpg` is quarantined, not accepted — asserted by test.
2. Images, then audio (disjoint signatures; images are the common case).
3. Everything else is `null`, which the caller turns into a `415`. The function does not choose an error code; the route does, because only the route knows the request context.

**Traps in `docs/15 §5.2`, each asserted:**

- **JPEG markers are enumerated, not masked.** Phase 4's own bug masked byte 4 to `0xF0`, accepting only the `Exx` family and rejecting DQT-first, SOF-first and Adobe JPEGs. Seven real marker values are tested.
- **WebP checks the RIFF *form type*, not the length field.** A WAVE container is refused; animated WebP is refused (`ANIM`/`ANMF`) while still WebP is accepted, because `VP8X` is the extended form and covers both.
- **PNG dimensions are read from IHDR and capped.** A 60 000×60 000 PNG fits in 5 MB and is the decompression bomb `§5.4` names. Out-of-range is a *rejection*, not "inconclusive" — "we could not confirm it is safe" is not a reason to store it.
- **`audio/webm` reads 64 KiB, not 4 KiB, and an inconclusive result is ACCEPTED.** `§5.2.4` makes the trade explicit: *"reject a valid 90-second voice note" is a worse failure than "accept a video-only WebM and let `<audio>` fail to play it."* The result is `confidence: 'inconclusive'` → `scanStatus: 'pending'`, which step 7 then refuses to serve to a responder.
- **`audio/mp4` is `ftyp` at offset 4, not 0.** Audio brands accepted, video brands refused, unknown brand refused rather than guessed.
- **MP3 accepts ID3v2 or a raw Layer III frame**, and rejects the `FF FF` polyglot marker `§5.2.6` names.

37 sniffer tests.

## 6. What is deliberately NOT built

### 6.1 `POST /api/incidents` — the create transaction

**This is the significant scope gap and it is named rather than worked around.**

`docs/15 §8.1` steps 5–7 live *inside* `POST /api/incidents`. Phase 3 built the incident **schema** but never the create pipeline. Phase 5 built steps 5 and 6 as a service (`attachEvidenceToIncident`) with the full `§16.3` semantics implemented and tested-by-construction, but **the route that would call it is not written**.

What this means concretely: a citizen can record, upload, verify and attach evidence, and the evidence lifecycle is correct up to the point of persistence — but the form does not yet submit a report. The wiring is prepared (`EvidenceUploader.onChange` → `draft.evidence`, which is what `canSubmit` reads, so the image-only path of `§16.3` keeps working), and the service is exported and ready.

**Why it was not written here:** it is a Firestore transaction, an audit write, a lifecycle status transition, a duplicate-detection hook, and a response envelope — a phase of its own. Building it in a rush at the end of this one would have been the wrong call, and a half-built create endpoint that can persist an incident without evidence is worse than none.

**Where it connects:** `services/uploads/evidence-attach.ts` exports `attachEvidenceToIncident(uid, incidentId, reportId, items, hasValidText)` and `resolveEvidenceRead()`. Both take the ids a transaction mints. Nothing else needs to change.

### 6.2 The staging sweeper

`docs/15 §16.2` specifies a `sweep-staging-uploads` maintenance job, manual trigger `POST /api/admin/maintenance/sweep-staging-uploads`, gated on `r57_runMaintenanceJobs`, audited. Phase 9 owns maintenance.

`sweepAbandonedStaging()` **throws** rather than returning `{ scanned: 0, deleted: [] }` — a caller receiving that would conclude staging is clean, which is a false statement. The contract for whoever builds it is written out in `SWEEP_NOT_IMPLEMENTED`, so the implementer does not re-derive it. brief §39: *"document it as a future integration point rather than creating an unsafe workaround."*

**Why the tempting workaround is wrong**, and it is wrong three ways:

1. Deleting a user's staging objects at incident creation does not touch the population the sweeper exists for — objects whose user abandoned the form. That is the overwhelming majority.
2. It puts a Storage **write** on the report-creation path, so a Storage blip could fail a report that was already filed — the exact outcome `§16.3` exists to prevent.
3. It creates a retention behaviour nobody chose, on evidence that may be needed for a dispute.

**Known residual** (`§16.2` row 3, D-13): if a transaction fails after the copy, an object exists at `incidents/**` that no `MediaRef` references. Not detectable yet; Phase 9's `sweep-orphaned-evidence`.

### 6.3 Virus and content scanning

`docs/15 §11` states the constraint honestly: no scanning is possible for a project at this stage. Compensating controls are implemented — the allow-list of six, executable/archive signatures quarantined, `nosniff`, `Content-Disposition`, and SVG/HTML absent entirely (removing the two formats where a payload would actually run). Residual risk **RR-10**.

### 6.4 EXIF stripping

`docs/15 §9.2` takes the honest position: stripping EXIF in the browser needs `createImageBitmap` + a re-encode, which is a quality loss and a main-thread cost, and a re-encode would destroy the original evidence the specification says must be preserved. `exifStripped` is recorded on the sign request **as a record, not a gate**.

### 6.5 No live STT

See §2.2. The seam exists; the implementation reads docs/09's by-product. Phase 6 can swap it for a real provider with no other change.

## 7. Storage

```
staging/{token.uid}/med_[A-Z2-7]{12}.{ext}                    ← the client PUTs here
incidents/{incidentId}/reports/{reportId}/med_[A-Z2-7]{12}.{ext}   ← Admin SDK, copy-then-delete
quarantine/med_[A-Z2-7]{12}.{ext}
```

`mediaId` is `med_` + 12 base32 characters from `crypto.randomBytes`. **Server-generated only** — a client-chosen id would be an enumerable, overwritable upload path. `bytes[i] % 32` is a modulo of 256 by 32, which is exactly uniform; the bias everyone worries about does not exist when the divisor is a power of two.

**Copy-then-delete, never a rename.** An interruption leaves a duplicate in `staging/` (swept in 30 min) rather than losing evidence (unrecoverable). The delete is last, with `ignoreNotFound: true`, and a failure there is a *warning* — the evidence is already at its final path.

**Why step 5 re-sniffs when step 4 already did** — not redundancy, a race:

```
sign → [attacker swaps the object] → finalize → [swapped again] → create
```

A signed URL lives 15 minutes. Finalize is seconds after sign; incident creation can be minutes later. A `MediaRef` recording a sniff from two minutes ago would attest to bytes that may no longer exist. Step 4 is a fast-fail; step 5 is authoritative, and its `sha256` is recomputed so a swap shows up as a difference.

### Limits

| Type | Ext | Max bytes | Per report | Total |
| --- | --- | --- | --- | --- |
| `image/jpeg` | `jpg` | 5 242 880 | 3 | **3** |
| `image/png` | `png` | 5 242 880 | 3 | **3** |
| `image/webp` | `webp` | 5 242 880 | 3 | **3** |
| `audio/webm` | `webm` | 15 728 640 | 1 | **3** |
| `audio/mp4` | `m4a` | 15 728_640 | 1 | **3** |
| `audio/mpeg` | `mp3` | 15 728 640 | 1 | **3** |

**Six values. That is the entire list.** `maxTotalPerReport` is 3, the same as the image limit — so a report with audio may carry at most two images. Stating one number is what stops a validator and a UI disagreeing about whether a fourth item fits.

### Storage security

`storage.rules` was written in Phase 2 and is already correct for Phase 5. It is verified, not assumed:

- `staging/{uid}/…` — `mine(uid)` for read/write/delete, so a user who guesses another uid gets nothing.
- Size and content-type caps are **in the rule**, because a rule is the only check a determined client cannot skip. `POST /api/uploads/sign` is *supposed* to check them; the rule is what makes the 15 MB cap a control rather than a suggestion.
- `incidents/**` and `quarantine/**` are `if false` for **everyone**, including admins. Only the Admin SDK can touch them, after an API authorization decision.
- The `&&`/`||` grouping in the size rule is parenthesised, with a comment explaining that an accidental precedence in a size limit is a size limit someone will eventually tidy away.

Ownership is `path.split('/')[1] === token.uid` — a **segment** comparison, so a uid of `abc` cannot claim `abcdef`'s uploads. A `startsWith` would. Tested both directions.

## 8. Voice

**Method:** `getUserMedia({ audio, video: false })` → `MediaRecorder`. Format negotiated via `MediaRecorder.isTypeSupported` across five candidates, in preference order: Opus WebM → WebM → `mp4a.40.2` → MP4 → MP3. **Safari's MP4 is last, not first** — it is the only format that reaches iOS, so putting it last costs nobody else anything.

The negotiated string is `;codecs=`-stripped before it reaches `contentType`, because the signed PUT's `Content-Type` must be byte-identical to what the signature covers. Sending `audio/webm;codecs=opus` when the signature covered `audio/webm` is a `403` naming a *signature*, not a format.

**Maximum: 120 s** (§2.3). Enforced by a `setTimeout`, not a tick check, because a tick only runs while the tab is visible — a citizen who switched away would come back to an unbounded recording.

**Pause** is offered only where `MediaRecorder.pause` exists on the prototype. iOS Safari has never had it, and a button that throws when pressed is worse than no button.

**Transcription** is docs/09's by-product (§2.2). `SpeechToTextService` has two methods and **neither one generates anything**, mirroring the `TriageProvider` discipline from Phase 4.

The thing that actually needed abstracting is not the model call — it is the translation of an outcome into one of four honest states:

| `status` | Means | Citizen is told |
| --- | --- | --- |
| `ready` | transcribed, not flagged | the transcript, editable |
| `uncertain` | transcribed, gaps flagged | the transcript, badged |
| `none` | audio attached, model got nothing | "I could not make out your recording" |
| `unavailable` | no provider, nothing attempted | "Voice transcription is currently unavailable" |

Conflating `none` and `unavailable` is the bug the file exists to prevent: the first says *your recording was too quiet* (the citizen's problem, fixable by speaking again), the second says *our provider is not configured* (nobody's problem, fixable only by typing). Sending someone to "speak up" when the real cause is a missing API key sends them in circles during an emergency.

Uncertainty comes from the model's `audio_transcript_uncertain` **flag**, never inferred from the text. A transcript that happens to contain "[inaudible]" is not thereby uncertain. And `unavailable` reports `uncertain: false` — nothing was attempted, so nothing is uncertain; claiming otherwise would imply someone listened.

## 9. AI integration

**One Gemini implementation. Nothing in Phase 5 creates a second.**

`services/uploads/evidence-attach.ts` exports `stageImageForAi()` and `stageAudioForAi()`, which download a *verified* object and hand it to Phase 4's existing `toTriageRequest` → `triageIncident` path.

The bytes pass through Phase 4's `validateImage` **a second time**, and that is not redundancy. Phase 4's validator is the only implementation of the signature check for the AI path. Storage's content-type check reads a **claim** the client made at PUT time; a `contentType: 'image/jpeg'` on an object full of HTML passes `storage.rules` and does not pass the validator. The three-layer chain — client pre-check, Storage rule, server sniff — exists because each layer checks something the others cannot.

The `MediaRef` records the **sniffed** type. The declared one is never persisted, never returned to the client as authoritative, and never sent to the model.

## 10. Duplicate-upload protection (brief §27)

Four causes, four mechanisms — "debounce the button" only fixes the first:

| Cause | Mechanism |
| --- | --- |
| double click | an in-flight `Set` keyed on a content fingerprint, checked **synchronously before any `await`** |
| React re-render | state lives in a module-level store, not `useState` |
| retry logic | a retry re-adds under a **fresh** `localId`, so it cannot collide with its own failed entry |
| component remount | the store is a module singleton, so a remount reattaches rather than starting empty |

The fingerprint is `name:size:lastModified` — the strongest identity a `File` carries for free. **Not** a content hash: sha256 of 15 MB on the main thread is a visible freeze on the device most likely to be filing this report.

The `useSyncExternalStore` binding in `report-form.tsx` replaced a `useMemo` on `[draft]` that I wrote and then rationalised in a comment. It was not reactive — a second copy of a fact the uploader already owns, which is precisely the class of bug this file is meant to prevent.

## 11. Emergency safety (brief §34)

No string anywhere in the speech service promises a responder. Enforced by a test **and** by security check #10, both scanning for: *"emergency services have been notified"*, *"help is on the way"*, *"responder(s) has been dispatched"*, *"alerted the authorities"*.

The most the UI ever claims is *"Your report is being prepared"*, *"AI analysis completed"*, *"Report ready for submission"*.

**Upload failures say the report has NOT been submitted** (brief §25). A failure message that omits that leaves a citizen believing their report is filed — during an emergency, the most damaging thing this phase could get wrong. `role="alert"`, not `aria-live="polite"`, because a failure is the one state that must interrupt.

It has been `tests/unit/ai/*` and `tests/unit/format.test.ts` on different runs — both untouched by this phase, both passing standalone (`format.test.ts`: 13 tests, 58 ms of test time, 5.12 s wall). The suite is green when run directly. **Not masked by raising the timeout**, because that would hide a real environment constraint rather than record it.

### Not tested — stated plainly

- **The Gemini call itself.** No `GEMINI_API_KEY` in this environment. Everything either side is covered by injected-transport tests (carried from Phase 4).
- **Any Firebase Storage call.** `signPutUrl`, the copy, the delete, the range read, `getStorage().bucket()` — all untested against a live bucket. The pure layers (sniffer, path contract, transcript states) are heavily tested; the I/O boundary is not exercised.
- **No DOM renderer is installed** (docs/02 §5 rejects adding one), so `EvidenceUploader` and `VoiceRecorder` are verified by their extracted pure logic — `preCheckFile`, `preCheckQuota`, `formatElapsed`, `stateLabel`, `classifyPermissionError`, `pickAudioMimeType` — not by rendering. The `xhr.upload.onprogress` path is likewise unexecuted.
- **No `POST /api/incidents`** to exercise end to end (§6.1).
- **Mobile breakpoints, screen readers, slow networks: untested.** No browser was driven.

## 14. Phase 6 integration points

1. **`POST /api/incidents`.** `attachEvidenceToIncident(uid, incidentId, reportId, items, hasValidText)` is written, exported and carries the full `docs/15 §16.3` asymmetry. The route mints the two auto-IDs, calls it, and persists the returned `MediaRef[]` inside its transaction.
2. **Duplicate detection.** `MediaRef.sha256` is computed over the whole object at both step 4 and step 5, specifically so Phase 6 can find "same file, different `mediaId`" without re-reading bytes. This was the reason the hash is computed at the authoritative moment rather than only at finalize.
3. **A real STT provider.** Swap `SpeechToTextService.fromTriageOutcome` for a `transcribe` method. Two implementations, a selection seam, no other change.
4. **The sweeper.** `SWEEP_NOT_IMPLEMENTED` carries the job name, the capability, the route, the window and a three-line contract.
5. **Evidence display.** `uploadsSignedUrl(mediaId)` is the only way to obtain a viewable URL. Any UI that shows a photo must fetch a signed URL first — one extra round trip, and the price of not persisting a credential.
6. **`MediaRef.storageMissing` / `storageCorrupt`.** Set by the read path so a dispatcher sees "evidence unavailable" rather than a broken image icon. The `storageCorrupt` half needs a client `onerror` handler and is not written.

## 15. Honest summary

Phase 5 is complete for **evidence handling**: capture, validation, transfer, verification, attachment and access control, with the security properties `docs/15` specifies and the tests to hold them.

It is **not** complete for **report submission**, because the create transaction was not written (§6.1). That is a real gap in the user-facing journey, named here rather than left to be discovered, with the service half built and the exact wiring documented.

The most valuable thing this phase produced is probably not a feature. It is the discovery that **a correct regex with no capture groups silently rejected every upload while passing every test that only called `.test()`** — and the security check written to make that specific mistake impossible to reintroduce.

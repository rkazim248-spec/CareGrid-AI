# 30.9 — Phase 8: Realtime Operations Dashboard

**Status:** foundation complete and tested; **the UI is not built** (§7)
**Precedence:** `docs/11` is a T0 anchor. It names module paths, a `ListenerId`
union, per-listener limits, a per-page budget, and a query-helper rule. All of
those are followed literally, and the two places it could not be are recorded in §2.

---

## 1. What this phase is

The realtime layer `docs/11` specifies: a listener registry that enforces a
budget, ten scoped query builders, a single attach primitive, and a connection
state that is *derived* rather than guessed.

`docs/11 §1.1`: "**the one decision**" is Firestore realtime listeners. That
decision was already made and Phase 8 implements it rather than re-deciding it.

**No `onSnapshot` existed anywhere in the project before this phase.** This is the
first layer of its kind.

## 2. Two places `docs/11` could not be followed literally

### 2.1 `onNetworkStatusChange` is not public API in the installed SDK

`docs/11 §4.2` derives `isReconnecting` from `onNetworkStatusChange(db, …)`.
**That function is not exported by `firebase/firestore` in 11.10.0.** It exists
only inside `@firebase/firestore`'s internal `remote/connectivity_monitor`, which
is not a public API and would break on any SDK upgrade.

So `firestoreStatus` is derived from the public surface: `window.online`,
`onSnapshotsInSync`, and a **stall detector** in `hooks/use-online-status.ts`.

**The stall detector is not a downgrade.** Firestore's connectivity monitor
reports what the transport *believes*; it does not report a socket that is open,
carrying no bytes, behind a captive portal. A dispatcher in that state is looking
at four-minute-old data, and "Reconnecting." is the honest indicator. The detector
answers precisely that question, using the one signal that proves liveness.

The two windows are deliberately different: staleness becomes true at 30 s
(the data is old), reconnection at 45 s (positive evidence of a stall). Conflating
them would show a banner before the data is actually misleading.

### 2.2 `docs/11 §11.2` forbids three fields on a live row

`Incident` has 40+ fields, and `slaState`, `ageMin` and `distanceM` are
**server-derived**. `docs/11 §11.2` puts them under "What MUST be delivered
through the API instead, and why" and calls that table "the single most important
security statement in the realtime design".

So `LiveIncidentRow` is a **declared subset**, and `LIVE_ROW_OMITTED_FIELDS` names
what it will never carry. A row type that structurally satisfied `Incident` would
make the omission invisible at the type level — which is where it would do the most
damage.

### 3.1 The store is keyed by id **and** queryKey — a bug the test found

The first version keyed `entries` by `ListenerId` alone. A second attach with a
**different** `queryKey` fell through the sharing branch and then **overwrote** the
first entry, so:

- the first component's channel was orphaned — its `detach` lost and its refcount
  gone, so its `unsubscribe` decremented a counter it was not counted in;
- the budget still reported **one** channel.

The symptom in the product would be a queue whose filters silently stopped
applying and which never closed its first socket. A test caught it; the fix is a
composite key, so "same id, different query" is honestly **two** channels and the
budget counts both.

### 3.2 `import.meta.env.MODE`, not `process.env`

`docs/11 §2.1` requires the budget to throw in a test. The project's own
`process.env is read only by the env accessors` security check **fired** on
`process.env.NODE_ENV === 'test'`, and it was right to — `lib/realtime/` reaches
the browser. `import.meta.env.MODE` is statically replaced at build time and
cannot become a runtime env read. `types/import-meta-env.d.ts` declares **only**
`MODE`, so declaring another becomes a reviewable act.

The default when `MODE` is absent is `'test'`, so a missing value makes the budget
**stricter**, never looser.

## 4. `lib/firestore/queries.ts` — Rule R-2, all ten builders

| | Builder | where | orderBy | limit |
| --- | --- | --- | --- | --- |
| L1 | `queueQuery` | dispatcher/admin | updatedAt\|createdAt | 50 |
| L2a | `incidentQuery` | any | — | 1 doc |
| L2b | `incidentHistoryQuery` | any | createdAt | 50 |
| L3 | `mapViewportQuery` | dispatcher/admin | updatedAt | 150 |
| L4 | `responderLocationQuery` | dispatcher/admin | capturedAt | 150 |
| L5 | `notificationQuery` | any | createdAt | 50 |
| L6 | `responderDispatchQuery` | any | dispatchedAt | 20 |
| L7 | `sessionUserQuery` | any | — | 1 doc |
| L8 | `kpiQuery` | dispatcher/admin | updatedAt | 20 |
| L9 | `slaSweepQuery` | dispatcher/admin | verifiedAt | 20 |
| L10 | `ownLocationQuery` | any | — | 1 doc |

Three decisions worth stating:

- **L1 uses `ACTIVE_STATUSES` (6); L3 uses `OPEN_STATUSES` (7, adds `resolved`).**
  The queue is the dispatcher's *work* and a resolved incident is not work. The map
  shows everything still on the map. `OPEN_STATUSES` is new in this file;
  `lib/collections/enums.ts` holds it so the two windows cannot drift.
- **L4 uses `!=` rather than `not-in`.** Firestore's `!=` excludes documents
  **missing** the field, so a `responderLocations` document written before
  `status` was denormalised onto it would silently vanish from the dispatcher's
  map. A dispatcher who cannot see a responder is worse than one who sees them
  with an unknown status.
- **L5 has no parameter to widen it** (`docs/11 §11.3` SEC-4). Not a default that
  could be overridden — no parameter exists.

The ops builders call `assertOpsRole`, which **throws** for a non-ops role. That
is UX protection and the function says so: the real boundary is `firestore.rules`,
which re-evaluates the ID token server-side and would deny the query whether or
not this function existed.

### 4.1 The builders use the free-function API

`FirestoreLike` was first declared as a structural subset with `collection` and
`doc` methods, so a test could pass a fake. That does not work in firebase 11,
where the public `Firestore` class exposes **no instance methods in its type** — the
API is the free functions `collection(db, path, …)` and `doc(db, path, …)`. So
`FirestoreLike = Firestore`, and the builders use the free functions. This is the
documented v11 style and it means a fake is no longer possible — which is honest,
because `docs/11 §12` wants listener assertions against the Emulator Suite, and
that suite hands these builders a real `Firestore` anyway.

## 5. `firestore.indexes.json` — nine indexes added, and why

An audit of the existing ten indexes against all **fifteen** listener query shapes
found **six uncovered**. An undeclared index is not a slow query: it is a
`failed-precondition` on the first snapshot, which `mapListenerError` reports as
"This view needs a database index that is not deployed" — i.e. the dashboard simply
never updates, with no error a user could act on.

| Missing | Why |
| --- | --- |
| L1 + `urgency in` | no urgency field in any index |
| L1 + `category in` | no category field in any index |
| L1 + `assigneeUid` | `docs/11 §2.2` calls this "index 5"; the shipped #5 is `users role` |
| L1 ordered by `createdAt` | index 1 orders by `updatedAt` |
| **L3** | **index 6 omits `deletedAt`** — QD-8 requires the `where` set to be a prefix of the index, so the shipped index is unusable for the query Phase 6 added the soft-delete filter to |
| L4 | no `status`/`capturedAt` index at all |
| L5 | index 9 carries a `read` field the query does not filter, and an index field the query omits cannot be used |
| L6 | index 8 omits `status` |
| L9 | no `slaBreachedAt` index |

19 indexes total. The header note now records the rule that made the additions
necessary: **every `where` clause must appear in the index, and every index field
must be used by the query.** Both directions fail identically.

### 6.1 Two existing checks fired on this phase's code, and were right

- **"process.env is read only by the env accessors"** caught
  `process.env.NODE_ENV === 'test'` in the registry. Fixed with
  `import.meta.env.MODE` (§3.2).
- **"No client-reachable file imports a server module"** caught an
  `AppError` import in `lib/realtime/listener-error.ts`. The fix removed the
  function: the mapping returns plain `{ code, message }` and a route builds an
  `AppError` from those two fields. Duplicating the error vocabulary in a client
  module would have been worse than the two-line conversion.

### 6.2 Two check bugs found by writing the checks

- Check 44's single-document exemption searched a 200-character window for
  `DocumentReference` and matched nothing, so it failed on two **correct**
  functions. Then the fix required a trailing `\{` that `declLength` excluded, so
  the exemption still never fired. An exemption that never fires is the worst shape
  for a check.
- Check 43's "per function" scan needed the return type from the declaration line
  separately, because matching the body alone cannot tell `incidentQuery` (one
  document) from `queueQuery` (a filtered list).

### 7.1 Why it was left out

The brief's UI requirements are inseparable from surfaces Phase 6 and 7 also did not
finish. `docs/12 §7` needs a live map; `docs/11 §2.2`'s L3/L4 need the map's
viewport logic; the KPI tiles need `DashboardTiles` derived from an L8 window whose
honesty labelling `docs/11 §14` RT-DR-3 calls out. Building a queue against mock
data and calling it live would have been the worse outcome: a green "Live" dot over
`MOCK_INCIDENTS` is the most damaging UI bug in the list, and the connection-state
work in §3 exists specifically to make it impossible.

### 8.1 The one thing a later phase must not do

**Do not widen L5.** `docs/11 §11.3` SEC-4 exists because a `?recipientUid=` in the
client path is a `permission-denied` waiting to happen, and a future rules change
that accidentally permitted it would be invisible. The structural guarantee is
check 46: the function takes two parameters and there is no third to add a selector
to.

### 8.2 The second thing

**`activeIncidentCount` and `assigneeUid` are denormalised, not computed.** Phase 7
maintains them transactionally and `firestore.rules` keys its read grant on
`assigneeUid`. A future phase that recomputes either would break the capacity check
(Phase 7 §5.2) or the responder's access to their own incident.

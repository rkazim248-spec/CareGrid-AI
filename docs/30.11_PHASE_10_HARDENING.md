# 30.11 — Phase 10: Security, Testing & Production Hardening

**Status:** one High finding fixed and mutation-tested; 19 new checks; **the Firestore
rules still have never been executed** (§5)
**Precedence:** this phase changes no product scope. brief §48 — no SMS, no WhatsApp,
no predictive AI, no route optimisation, no IoT, no weather APIs, no native apps, no
autonomous dispatch, no paid services.

## 1. What this phase actually did

Three things, and one deliberate non-thing.

1. **Fixed a real cross-account data-exposure defect** (§2).
2. **Made 19 silent-failure invariants mechanically checkable** (§3).
3. **Fixed a bug in the checker itself** that was letting checks pass on files not in
   the build (§4).
4. **Did not** add the emulator, the E2E suite, or any UI. §5 says why, and what it
   costs.

Everything else was audit. The codebase was already substantially hardened — deny-by-
default rules, `server-only` boundaries, a non-interpolated system instruction, a
Firestore-backed rate limiter, a non-parameterised CSP. The audit records those as
**verified correct** rather than manufacturing findings to justify the exercise.

## 2. The defect: `unsubscribeAll()` had no caller

`lib/realtime/listener-registry.ts` exported `unsubscribeAll()` from Phase 8. Through
Phase 9 it had **zero callers**, and the registry's own docstring already said it "is
callable from `hooks/useAuth.ts`'s `onAuthStateChanged` handler" — the intent was
documented and the wiring never landed. (`hooks/useAuth.ts` does not exist; auth lives
in `lib/firebase/auth.ts`.)

A Firestore `onSnapshot` is a subscription with a **captured credential**; its query
is fixed at subscribe time. In this app those queries are user-scoped:

| Listener | Query | What it holds |
| --- | --- | --- |
| L5 `notifications` | `where('recipientUid','==',uid)` | one person's private correspondence |
| L1 `queue` | active statuses, live | the dispatcher's incident queue |
| `responderAssignments` | per responder | the dispatch board |

`clearUserScopedStorage()` — the sign-out path — reaches `localStorage` and
`sessionStorage`. A live listener is not storage. So a dispatcher who signed out on a
shared machine without closing the tab left their queue, board and notification list
in every consumer's `state.items`, and a second person signing in rendered it while
their own data loaded.

The same window existed for a token revoked from the console, a session terminated by
`disableSignIn`, and an account switch in a second tab — none of which route through
the app's own `signOut()`.

### 2.1 Why the decision is its own module

The rule is four cases and one boundary condition, and it is wrong in a way nobody
would notice by reading it. So `lib/realtime/identity.ts` decides and
`lib/firebase/auth.ts` acts:

```ts
decideListenerTeardown({ previousUid, nextUid, hasResolvedOnce })
  → { teardown, reason, closingUidFor }
```

`hasResolvedOnce` is **load-bearing**. `previousUid === null` is ambiguous between
"boot, nothing seen yet" and "the last user left", and those need *opposite*
behaviour — the first must not tear down (nothing is open, and tearing down races the
listeners about to open), the second must.

| Event | Teardown | Why |
| --- | :-: | --- |
| first resolution | no | nothing open yet |
| **same uid (token refresh)** | **no** | fires ~hourly; closing is churn for no gain |
| `null` → uid | no | the new listeners have not opened |
| uid → `null` | **yes** | channels must not outlive the user |
| **uid A → uid B** | **yes** | A's channels are still bound to A's queries |

The token-refresh row is the one that keeps this from being a bug in the other
direction. `onAuthStateChanged` fires on every ID-token refresh, roughly hourly for
every signed-in user; a teardown keyed on the *event* rather than the *identity*
would close and reopen every channel once an hour.

### 2.2 Two call sites, deliberately

`signOut()` covers the path the user takes. `handleAuthStateOrIgnoreError` — the single
funnel every auth handler in the app passes through — covers the four paths they do
not. Wrapping the handler rather than adding a second `onAuthStateChanged` avoids
keeping a second subscription alive for an event the first already delivers.

Two orderings, both load-bearing:

- **`signOut()` tears down BEFORE `fbSignOut`.** `fbSignOut` resolves only once the
  token is gone, so anything reading listener state in that window would find the old
  channels attached. Tearing down first makes the window empty rather than short.
- **The auth handler tears down BEFORE invoking the subscriber**, so a re-render on
  sign-out never paints one frame of the previous account's notifications.

## 3. New verification: 116 → 135, all mutation-tested

**19 new checks. 16 distinct mutations. 16 caught.** A check that cannot fail is not a
control, so each was proven to fail when its target is broken.

| Check | Invariant | Mutation proved |
| --- | --- | --- |
| C75 | `signOut` closes listeners **before** `fbSignOut` | order, not presence |
| C76 | `onAuthStateChanged` also tears down on an identity change | `if (false && decision.teardown)` |
| C77 | a same-uid refresh and the first resolution do **not** tear down | removing the guard |
| C78 | every mutating handler declares a rate limit | deleting a `rateLimit` key |
| C79 | an unlimited GET records the decision as an infinite rule | removing the reference |
| C80 | a finite rate-limit rule is attached to a route | pointing a route at a dead key |
| C81 | `SYSTEM_INSTRUCTION` has no interpolation | injecting `${...}` |
| C82 | untrusted text is wrapped **and** delimiters defanged | — |
| C83 | AI output is Zod-validated, confidences 0–1 | — |
| C84 | `users/{uid}` refuses all client writes | `if isSelf(uid)` |
| C85 | `auditLogs` is append-only | `if isAdmin()` |
| C86 | Storage denies by default; staging size+MIME capped | — |
| C87 | no script-injection sink anywhere | adding `.innerHTML =` |
| C88 | the server fetches no user-supplied URL | — |
| C89 | no navigation from a user-supplied URL | — |
| C90 | `GEMINI_API_KEY` read only by the `server-only` module | renaming the accessor; adding one to `env.client.ts` |
| C91 | `lib/env.client.ts` reads only `NEXT_PUBLIC_*` | a private name |
| C92 | all 8 required headers set in one place | renaming one |
| C93 | no `'unsafe-inline'` in `script-src`; `'unsafe-eval'` dev-only | adding the directive |

### 3.1 Four checks that passed for the wrong reason

Every one was found by mutation testing, not by reading. This is now the fourth phase
where that has happened, so the pattern is worth stating: **a check that cannot see its
target reports success.**

1. **C90 matched the wrong access idiom** and reported **zero** reads for a key read
   eight times. The real forms are `optionalString('GEMINI_API_KEY')` and
   `GEMINI_REQUIRED_VARS = ['GEMINI_API_KEY']`, and the pattern was shaped for
   `process.env`. A security check that says "no exposure" because it cannot see the
   exposure is worse than no check at all.
2. **C78/C79 iterated route option blocks without pairing them to a method**, so
   `api/me`'s rate-limited PATCH was flagged against its unlimited GET. A correct
   implementation failing a check written to catch an incorrect one — the failure mode
   that makes teams disable checks.
3. **C93 scanned the middleware with comments in**, and flagged the codebase's own
   explanation of why `style-src` may use `'unsafe-inline'`. To make it pass, someone
   would have had to **delete the explanation**.
4. **C84 asserted the Firestore verbs `read`/`query`**; the rules use `get`/`list`, so
   the pattern never matched and the check was vacuously true.

### 3.2 Three invalid mutations, and why they matter

Three of sixteen "misses" were **my mutations failing, not the checks**:

- A "removal" that kept the text (`RATE_LIMIT_RULES['me.read']` plus a comment marker
  still contains the substring).
- `String.replace` replaces the **first** occurrence only, so a mutation of
  `allow update, delete: if false;` hit a different match block and never touched
  `auditLogs`.
- `lib/env.server.ts` reads the key in **two** places; changing one left the other.

A mutation that does not change behaviour cannot fail a check. Every mutation in this
project is now written to assert that it altered the target before the result is
believed.

## 4. A bug in the checker

`SKIP` omitted `.kilo`, which holds a full stale copy of the project from an earlier
phase — so **every check was reading two copies of most files.**

This is not cosmetic. A check can be satisfied by a line in a worktree that is not part
of the build, and a mutation test can appear not to trigger because a second copy of
the target still holds the original text. It surfaced concretely: C90 reported the
Gemini key read by six modules, three of them in `.kilo`.

Fixed by adding `.kilo`, `.vercel` and `out`. Separately, `SCANNED` now normalises
paths to forward slashes, because `path.join` yields backslashes on Windows and a
downstream `file.startsWith('tests/')` silently stopped matching — which is how two
checks came to count **test files** as production modules.

## 5. What was NOT done, and what it costs

### 5.1 The Firestore and Storage rules have never been executed

The single largest gap. 135 checks verify the rules **structurally** — that
`users/{uid}` denies writes, that `auditLogs` denies update, that the Storage catch-all
denies. No check has ever *evaluated* them, and structural reading cannot catch a rule
that is well-formed and wrong: a `&&`/`||` precedence slip, a helper that returns the
opposite of its name, a `hasOnly` list missing one field.

**Blocked by the environment, not by the project.** The Firestore rules emulator
requires a **Java runtime**; neither `java` nor `firebase-tools` is installed. The
emulator ports are already configured in `firebase.json` (auth 9099, firestore 8080,
storage 9199), so the blocker is the toolchain.

`docs/SECURITY_AUDIT_REPORT.md` §9.1 specifies the full deny/allow matrix that should
be asserted — per collection, per role, allowed **and** forbidden — so the work is
ready to execute the moment a JDK exists. brief §36 says "if Firebase Emulator testing
is available, use it"; it is not available here.

### 5.2 Also not done

| Item | Why |
| --- | --- |
| **E2E suite** | brief §37. The scenario is covered by unit and integration tests over mocked boundaries, not by a running application. Writing a suite that mocks every boundary would test the mocks. |
| **Browser verification** | No browser. CSP enforcement, `Permissions-Policy`, COOP and the Google sign-in popup are unverified. |
| **All 7 responsive breakpoints** | brief §40. Nothing was rendered. Layout was reviewed by reading the CSS, which is not the same as seeing it. |
| **Accessibility** | brief §39. No `axe` run, no keyboard pass, no contrast measurement, no screen reader. |
| **Performance measurement** | No load test, no Lighthouse. The listener budget and query bounds are unit-tested; real read counts are inferred from query shape, not observed. |
| **Rules weakening** | **None.** Every fix in this phase tightened a control. No rule was relaxed to make a test pass. |

### 5.3 Two decisions deliberately left to the deployment owner

1. **`postcss`** — a High advisory, but not a production dependency, imported by **no
   application file**, and both its advisories require attacker-controlled CSS
   stringify. The fix is a `next` major, which brief §32 says not to force. Pinning or
   overriding is a judgement about accepting an upstream advisory in exchange for
   stability — not a blind upgrade, and not a silent one.
2. **Emulator tooling** — a JDK plus `firebase-tools` is a real install. §5.1 is the
   largest unverified surface, so it is worth it; it is not free and not small.

## 7. What Phase 11 should do, in priority order

1. **Install a JDK and `firebase-tools`; execute the rules.** §9.1 of the audit is the
   written specification. Everything about rules in this project is currently
   structural, and a structural claim is weaker than an executed one.
2. **Render it.** All 7 breakpoints, keyboard traversal, focus trapping, contrast,
   screen-reader labels, and the map's non-visual fallback. A `docs/25` claim is not a
   measurement.
3. **External configuration, before any deploy.** Restrict the Maps browser key by
   referrer and required APIs, restrict the server key by IP, configure authorised
   domains, and **deploy the 19 indexes**. An un-deployed index is the nastiest
   failure in the list: the query fails as `failed-precondition` and the UI renders
   "not enough data" — a quiet failure that looks like a quiet week.
4. **Finish `/api/analytics`.** Still `MOCK_ANALYTICS`; the engine from Phase 9 is
   ready and the type is honest, but the route, the rollup writer and the risk-zone
   recompute do not exist.
5. **Write the data-retention policy** brief §46 asks for. None is set, which is the
   correct default — safety and audit data must not be auto-deleted without explicit
   product approval — but a documented policy is still owed.
6. **A real E2E run**, once something renders.

# 30.4 — Phase 3: the backend foundation

> **Written after the code.** Phase 3 built the backend/API foundation every later phase uses:
> the request pipeline, centralized validation, centralized authorization, a rate limiter, a
> service layer, the Firebase server architecture, the environment-variable system, and the
> connection points for Gemini, Google Maps, and Twilio.
>
> **This document records what was built, the six places the code and the documentation had to be
> reconciled, the three real bugs it found, and what was deliberately NOT built.** It follows the
> pattern of [30.2](./30.2_PHASE_2_IMPLEMENTATION.md) and [30.3](./30.3_PHASE_2_DOC_AMENDMENTS.md),
> because a phase record nobody wrote is a phase nobody can audit.
>
> **A note on the phase number.** The Phase 3 brief for this build is the *backend foundation*.
> [30 §6](./30_DEVELOPMENT_PHASE_PLAN.md) calls Phase 3 "Database + incidents" — the create
> pipeline, the lifecycle table, the duplicate engine. Those are **not** in this build and are not
> claimed to be. The brief is the authority on sequencing; the documentation is the authority on
> identifiers. Where the two used the same word for different things, the brief won the sequence
> and this document records it, because a reader who opens doc 30 expecting the create pipeline
> deserves to be told plainly that it is Phase 4 and 5 work.

---

## 1. What Phase 3 is, in one paragraph

A request that reaches a route handler now passes through one wrapper that mints a request id,
refuses a cross-origin state change, counts the caller against a bucket, verifies the ID token
and reads the **authoritative** role from Firestore, validates the body, the query string, and the
path parameters, hands the handler typed data and a service, and converts anything thrown into a
standardised envelope with the right HTTP status — and no stack trace, no Firebase internals, and
no secret ever leaves the server. The business logic that used to live inside the four Phase 2
route handlers now lives in `services/`, so adding a fifth route to the same contract is a
fifteen-line file. And Gemini, Google Maps, and Twilio each sit behind a typed interface with
their secrets read in exactly one file, so Phase 4 and Phase 6 are implementations rather than
restructures.

## 2. The request pipeline

`lib/server/route.ts` → `withRequest(options, handler)`. docs/06 §3.1 and docs/10 §6.3 specify the
order; it is not a style preference.

| # | Step | File | Failure |
| --- | --- | --- | --- |
| 0 | Admin precondition | `lib/env.server.ts` | `503 SERVICE_UNAVAILABLE` |
| 1 | Mint or adopt `requestId` | `lib/server/http.ts` | never fails |
| 2 | Same-origin, non-GET | `lib/server/http.ts` | `403 CSRF_FAILED` |
| 3 | Rate limit — **skipped when the Admin SDK is unconfigured** (see §5.4) | `lib/server/rate-limit.ts` | `429` + `Retry-After` |
| 4 | Authenticate | `lib/server/auth-guard.ts` | `401` / `403` |
| 5 | Authorize | `lib/server/permissions.ts` | `403 FORBIDDEN` |
| 6 | Validate body, query, **params** | `lib/server/validate.ts` | `400` / `413` / `415` |
| 7 | Run the handler | the route file | domain `AppError` |
| 8 | Timeout race | `lib/server/route.ts` | `504 TIMEOUT` |
| 9 | Envelope + headers + log | `lib/server/route.ts` | never fails |

Three orderings were each chosen against the obvious alternative:

- **Auth before validation.** An anonymous prober learns nothing about the schema.
- **Authorization before rate limiting** is documented but **not** what is implemented, because
  the bucket is keyed on the uid, which does not exist until after step 4. The rate limit runs
  first, keyed on the **unverified** `sub` claim, and the role gate still runs after it. See
  §6 D-4.
- **Validation before any I/O** (FR-142). A malformed body costs one CPU pass, not a database
  round trip. Asserted over every route: none imports the Admin SDK.

### 3.1 `GET /api/auth/me` — a documented alias, not an invention

docs/32 MUST NOT 2 forbids an endpoint that is not in docs/08. `/api/me` is the documented path
and it stays canonical; the client keeps calling it. `/api/auth/me` exists because it is the path
a reader expects next to `/api/auth/event`, and because the service layer now makes it a
fifteen-line delegation rather than a hundred-and-twenty-line copy. **A copy is what makes "why
does the header show a different name from the profile page" happen**, and that is the reason the
service extraction happened in this phase rather than the next.

`GET /api/auth/me` is recorded in [08 §14](./08_API_SPECIFICATION.md) as amendment **A-4**.

### 3.2 `POST /api/ai/triage` — the architecture probe

It returns the documented **fallback** outcome, because no Gemini key is configured. That is the
point, not a gap:

```text
POST /api/ai/triage
     ↓ withRequest        rate limit → authenticate → validate
     ↓ requireCapability  r13_readAiTriagePanel
     ↓ services/ai        the TriageProvider seam
     ↓ services/integrations/gemini   no key → no client
     ↓ 200 with source: "fallback", needsReview: true, providerAvailable: false
```

The alternative — a fabricated `urgency: 'critical'` — is what docs/32 MUST 6 forbids, and for
*this* product specifically a fabricated triage decision on a real emergency report is worse than
an honest failure. **There is no `if (DEV) return FAKE_DATA` branch anywhere in the path**, and
`scripts/security-check.cjs` fails the build if one appears.

### 3.3 What was NOT created, deliberately

`app/api/incidents/`, `responders/`, `dispatches/`, `maps/`, `notifications/`, `uploads/`,
`analytics/`, `admin/users/`, `cron/` — **not created**. They are listed in
[34 §7](./34_BACKEND_INTEGRATION_POINTS.md) with the exact file each will need.

An empty route folder is not architecture; it is a directory that reads as progress. The brief
said "do not create empty folders just for appearance", and docs/32 MUST 14 says a layer with no
caller is dead code.

## 4. The service layer, and the extraction

`services/` at the repository root, per docs/20 §1 P4. `services/index.ts` is the **only** import
path into it, and only `app/api/**` uses it.

| Domain | File | Exported |
| --- | --- | --- |
| auth | `services/auth/account.ts` | `bootstrapUser`, `getMe`, `updateMe`, `recordAuthEvent` |
| admin | `services/admin/system-health.ts` | `systemHealth` |
| ai | `services/ai/triage.ts`, `services/ai/index.ts` | `triageIncident`, `toTriageRequest`, `TRIAGE_LIMITS` |
| integrations | `services/integrations/{gemini,google-maps,twilio}/index.ts` | the provider accessors |

Before Phase 3 the four route handlers held their own Firestore access inline. Nothing was
functionally wrong; the problem was that the same logic was about to be needed by a second route,
and a copy is how two implementations of a security-relevant contract drift.

**There is no `lib/repositories/` layer, and the brief asked for one.** See
[34 §4.1](./34_BACKEND_INTEGRATION_POINTS.md) for the full reasoning: docs/20 P3 declares `lib/`
pure, docs/06 §2.2 forbids `firebase-admin` outside `lib/firebase/*`, and docs/06 §5.1 gives data
access to services. In this architecture `services/` **is** the repository layer.

## 5. The five real bugs Phase 3 found

Each was found by writing a test or a mechanical check, and each is now pinned by one.
**Three were pre-existing; two were introduced by this phase and caught by its own suite.** Both
categories are listed, because a record that only lists the easy ones teaches the wrong lesson.

### 5.1 `NOTIFICATION_DISABLED` was missing from the error catalogue

`PATCH /api/me` threw it (docs/30.3 §A6.1 documents the code), but `ERROR_STATUS` had no entry,
so `statusForCode()` fell through to **500**. A user toggling a notification switch was told
"Something went wrong" instead of being told the field and why.

*Found by* writing `tests/unit/api/error-codes.test.ts`. *Fixed in* `lib/api/error-codes.ts` ->
`NOTIFICATION_DISABLED: 422`. *Pinned by* the same test.

### 5.2 `AI_UNAVAILABLE` was 503; docs/16 §3.6 says 502

The request was well-formed and we reached a third party, so the fault is upstream. A 503 tells
a client to back off, which is right for a database and wrong for a provider whose quota is not
the caller's problem.

The existing test pinned 503. **The test was wrong and the catalogue was right**, so the catalogue
was corrected to match the anchor document and the test was corrected to match the catalogue —
with the reasoning recorded in the test rather than the assertion quietly dropped (docs/32 §3.10
permits exactly this: fix the test *because an anchor document says it was wrong*, and amend the
anchor in the same change). The replacement assertion is **stronger**: it now checks the whole
family that means "we could not do it" and requires each to be 5xx-but-not-500.

### 5.3 `Permissions-Policy` was blocking two product features

`middleware.ts` set `camera=(), microphone=()`. That blocks `ENABLE_VOICE_REPORTING` (FR-009)
and image evidence (FR-005) **at the browser, permanently**, for reasons invisible in the code
that uses them. docs/10 §15 specifies `(self)` for both. `Cross-Origin-Opener-Policy` was also
absent, and its browser default of `same-origin` severs the window handle `signInWithPopup` needs
— so Google sign-in was broken under a policy nobody had added yet.

*Found by* writing `tests/unit/api/security-headers.test.ts`. *Fixed in* `middleware.ts`. *Pinned
by* the same test.

### 5.4 `GET /api/health` would have 503'd in an unconfigured deployment

**This one was introduced by Phase 3 and caught by Phase 3's own test suite.** It is recorded at
length because it is the most instructive failure in the phase.

`GET /api/health` declares a rate limit, so `withRequest` reached `applyRateLimit` ->
`enforceRateLimit` -> `getAdminDb()`. The Admin SDK bootstrap throws `SERVICE_UNAVAILABLE` when
the credentials are absent — which is correct — and the liveness endpoint therefore answered
**503 for exactly the condition it exists to describe**.

That defeats the entire purpose of the `allowUnconfigured` option, and it reintroduces the precise
failure mode `tests/unit/unconfigured-deployment.test.ts` was written in Phase 2 to pin. The
Phase 2 suite did not catch it, because it asserts accessors and status codes rather than the
pipeline.

**The fix:** the rate limit is skipped when the Admin SDK is not configured, because the bucket
lives in Firestore. A limit that cannot be stored cannot be enforced, and pretending otherwise is
worse than saying so.

**The general lesson, which is why it is written down rather than just fixed:** adding a step to
the pipeline can break a step that was already correct, and the two are far apart in the function.
`tests/unit/api/route-pipeline.test.ts` now asserts the gate **and** asserts that the rate limiter
still reaches Firestore, so if a future change removes the Admin-SDK dependency from the limiter,
the test says the gate can go too.

### 5.5 `types/api.ts` put a server module in a client import graph

`types/api.ts` is reachable from a Client Component, and it re-exported `RequestContext` and
`RouteHandlerContext` from `@/lib/server/route`. Type-only, so nothing leaked at runtime — but it
is exactly the layering violation docs/05 §4 exists to prevent, and the day someone changes one of
those to a value import, the Admin SDK is in a browser bundle.

`scripts/security-check.cjs` found it, on the first run of the new check that looks for
client-reachable files importing `@/lib/server/**`. Both re-exports are gone, and the reason they
are absent is written in the file so nobody helpfully adds them back.

**A second, smaller duplicate went with it:** `ApiErrorDetail` was declared in BOTH
`lib/api/envelope.ts` (derived from its Zod schema) and `lib/server/validate.ts` (hand-written).
Two definitions of one contract is one too many, so the type is now declared once and re-exported.
That is the whole argument for deriving a type from a schema rather than writing it twice.

## 6. The six reconciliations

Where the documentation and the current code disagreed, one of them had to give. Each is recorded
here and, where it changes a document, in that document.

### D-1 — `lib/api/validate.ts` (doc 06 §3.9) is `lib/server/validate.ts`

**Conflict.** docs/06 §3.9 puts request parsing in `lib/api/`; docs/10 §6.1 and docs/30 §6.2 task
3.9 put `rate-limit` and `serialize` in `lib/server/`.

**Resolution: `lib/server/`.** Phase 2 established `lib/server/*` as the home for server
plumbing, and docs/30 — the phase plan, and the most specific document for this work — says
`lib/server/`. `parseJsonBody` reads a `Request`; it is server-only. A re-export barrel at the
documented path would create two names for one thing, which is worse than one name in the wrong
place. **Amend docs/06 §3.9 to `lib/server/validate.ts`.**

### D-2 — `lib/server/logging.ts` is a three-export barrel over `lib/server/http.ts`

docs/10 §16.3 and docs/32 MUST NOT 9 name `lib/server/logging.ts` as the module that redacts.
Phase 2 put the logger in `http.ts` beside the request id and the CSRF check.

**Resolution: the barrel exists, and it is not a stub.** A contributor who reads docs/10 §16.3
and greps for `logging.ts` finds a file whose every line explains why the redaction is an
**allow-list** rather than a deny-list — the single most important property of the logger, and the
one a future change is most likely to weaken.

### D-3 — The error envelope keeps `meta`, not `error: null`

The Phase 3 brief shows `{ "success": true, "data": {}, "error": null }`. docs/08 §1.2 (a T0
anchor) specifies `{ "success": true, "data": {...}, "meta": { "requestId": "req_…" } }`.

**Resolution: docs/08 wins.** The anchor documents outrank a brief, and the reason is functional:
`meta.requestId` is on **both** paths, so support can trace a failure even for an error code the
UI has no branch for. `error: null` on every success would be a field that is always null and
never carries information.

### D-4 — The rate limit runs BEFORE authorization, keyed on the unverified `sub`

docs/10 §6.3 places the rate limit at step 12 and the resource gate at step 14, with the role
gate at step 9 — so rate limiting comes **after** the role gate. The implementation runs it
**before** authentication, because the bucket is keyed on a subject and the uid does not exist
until after step 4.

**Resolution, and the reasoning matters:**

- The subject is the **unverified** `sub` claim, read without verification. That is safe **for a
  rate-limit subject and nowhere else**: it selects a bucket, and `requireUser` still does the
  real verification before the handler runs. A forged token yields a forged bucket, which means
  no limit for that attacker — so the uid is used only when a token is present, and an anonymous
  caller falls back to the **salted IP hash**, then to a route-scoped global bucket. A shared
  bucket is a worse experience for a legitimate user; a missing bucket is worse for everyone.
- The order is a documented compromise, not an oversight: a caller with no permission **can** burn
  another subject's quota by hitting a route it is refused. Phase 4 revisits this when
  `POST /api/incidents` exists and its limit is the one that matters (5/h, 20/day, FR-015).
- **Amend docs/10 §6.3** to state that the rate-limit subject is the unverified `sub` and that the
  step is "before the handler, after the token is present".

### D-5 — `config/collections.ts` holds 14 top-level collections, not the 15 docs/07 §1 claims

The authoritative cross-reference is **`firestore.rules`**, not a count in prose. The rules file
has 14 top-level `match` blocks plus `config/{configId}`. `config/collections.ts` mirrors them and
adds `notificationReads` (docs/07 §10.1), which has **no rule yet** — so it is CLOSED, not open,
because of the deny-by-default catch-all.

`tests/unit/api/environment.test.ts` cross-references the table against the rules file in **both
directions**, so a collection with a rule and no constant (a magic string) and a constant with no
rule (an unwritten rule) both fail a test. That is more useful than a hard-coded count, and it
cannot drift.

### D-6 — `lib/integrations/contracts.ts` is pure, so it has NO `server-only` guard

Every other server module carries `import 'server-only'`. The contracts file must not: it is the
one file a Client Component and a unit test are both allowed to import, which is the entire reason
it is a pure interface file. Its protection is **pureness** — there is nothing in it to leak.

Both the exception and the purity are asserted in `scripts/security-check.cjs`, so adding the
guard (which would break the map and the tests) or adding an import (which would leak) both fail.

## 9. Post-flight answers

The five questions docs/32 §5 requires.

**What changed and why.** A backend foundation: one wrapper owning the whole request pipeline, a
service layer so route handlers are thin, centralized validation, authorization and rate limiting,
a role-aware health endpoint, and three provider boundaries with their secrets read in one file
each. Why: because Phase 4, 5, 6, and 9 all need these, and building them under deadline is how
an authorization bug happens.

**What was considered and rejected.**

| Option | Rejected because |
| --- | --- |
| `lib/repositories/` | docs/20 P3 declares `lib/` pure; docs/06 §5.1 gives data access to services. See [34 §4.1](./34_BACKEND_INTEGRATION_POINTS.md) |
| `lib/integrations/{gemini,google-maps,twilio}/` as adapters | an adapter that calls a provider is I/O, and `lib/` may not do I/O. `lib/integrations/contracts.ts` holds the PURE interfaces; `services/integrations/*` holds the adapters |
| An in-memory rate limiter | documented as unsafe on a stateless platform; `serverEnvProblems()` reports it as a fault rather than honouring it |
| A fail-OPEN rate limiter | a Firestore blip would silently remove the only spam control on `POST /api/incidents`. Fail-closed: if the datastore is down, a route that reads it cannot work anyway |
| A `NEXT_PUBLIC_GEMINI_API_KEY` | the brief explicitly forbids it, docs/21 §1 forbids it, and `serverEnvProblems()` treats a `NEXT_PUBLIC_` value containing `-----BEGIN` as a fault |
| A real `@google/genai` dependency | a dependency with no caller is a dependency nobody has justified (MUST 3, docs/31 §14) |
| A generic `lib/api/errors.ts` refactor of `lib/server/errors.ts` | the server funnel and the client error are different concerns with different invariants. Only `ApiError` moved, and only because a component needed the type without the fetch machinery |
| `viper`-style config validation for everything | the project already validates with Zod; adding a second validator is docs/17 §15 anti-pattern territory |

**What could break, and how it fails.**

| Risk | Degraded path |
| --- | --- |
| Firestore unavailable | `503 DB_UNAVAILABLE` on every route that needs it; `/api/health` still answers `200` |
| Gemini unavailable | `502 AI_UNAVAILABLE`; the report is still recorded with `triageSource: 'fallback'` |
| Maps unavailable | `502 MAPS_UNAVAILABLE`; the map renders without place names and the **list is unaffected** |
| Twilio unconfigured | `422 NOTIFICATION_DISABLED`; in-app notifications unaffected |
| The Admin SDK unconfigured | `503 SERVICE_UNAVAILABLE` naming the three variables; `/api/health` still answers |
| A handler exceeds `REQUEST_TIMEOUT_MS` | `504 TIMEOUT` with the standard envelope and a `requestId`, not a platform 504 with no body |
| A provider throws something unexpected | caught in `triageIncident()`, logged at `warn`, fallback returned; the report is never lost |

**What was NOT done, and what it would take.**

| Not done | Phase | What it would take |
| --- | --- | --- |
| The Gemini prompt, schema, rules, and fallback engine | 4 | files in `services/ai/`; the seam is ready |
| The Maps Geocoding API calls | 6 | one file behind `GeocodingProvider` |
| The Twilio SDK calls | 9 | two channels behind `NotificationChannel` |
| The incident create pipeline, lifecycle, duplicates | 4/5 | `services/incidents/**`, `lib/incidents/**`, `lib/geo/**`, `lib/duplicates/**` |
| Realtime listeners | 6 | `lib/firebase/listener-registry.ts`; the CSP already permits the transport |
| `GET /api/admin/users`, `/api/incidents`, etc. | 4/5/6/9 | routes, each a thin wrapper over a service |
| Emulator-backed integration tests | 10 | `tests/integration/**` and a Java runtime |
| `POST /api/incidents/:id/reports` | — | still an open `DECISION REQUIRED` in docs/17 D-17-10. Not built. |

**What is uncertain.** The rate-limit ordering compromise (D-4) is the one to revisit first in
Phase 4, when `POST /api/incidents` exists and its 5/h + 20/day limits are the ones that matter.
It is marked provisional; this build does not have the authority to close it.

# 30.3 — Phase 2 amendments to the normative documents

> **Written 2026-09-26, after the code.** Phase 2 built the authentication layer and found
> seven places where the documentation was incomplete, self-contradictory, or wrong. This
> file records each one so the docs can be amended **in place** by whoever owns them, and
> so a reader who notices the gap knows it was found rather than missed.
>
> **Nothing here changes the design.** Every item is either a clarification, a resolution of
> a conflict the consistency report already flagged, or the recording of a decision that had
> to be made because the documents did not cover the case.
>
> Each entry names the file and section to amend, the text as it stands, and the text as it
> should read.

---

## A1. `docs/05_FRONTEND_ARCHITECTURE.md` §9 — the middleware cannot do what §9.1 says

**The conflict.** §9.1 describes Edge middleware reading "the `__session` cookie's existence,
or a Firebase session cookie verified via `getSession()`". §9.2 then says the middleware "is a
redirect convenience only. It is never a security control." Meanwhile
[10 §12.1](./10_AUTHORIZATION_SECURITY.md) and §12.3 state that **this product attaches no
session cookie at all** — every API call carries `Authorization: Bearer <Firebase ID token>`,
deliberately, because a cookie is an ambient credential that a cross-origin page can cause the
browser to attach and a bearer header cannot.

§9.1 offers a fallback ("**or**"), so it is not strictly a contradiction. But implementing the
first option would have required inventing a session cookie, which §12.3 rejects on security
grounds. A middleware that redirects on a cookie it cannot verify is a control that *looks* like
one — worse than none, because a team would then believe the Edge protected the routes.

**What to amend.** In §9.1, strike the session-cookie option and state the actual reason:

> **Amended §9.1.** This product has no session cookie ([10 §12.1](./10_AUTHORIZATION_SECURITY.md)),
> so there is nothing for Edge middleware to read. The authoritative role lives in
> `users/{uid}.role`, and the Firestore Admin SDK — the only way to read it — does not run on
> the Edge runtime. `middleware.ts` therefore sets **response headers only** (CSP, HSTS,
> `X-Frame-Options`, `Referrer-Policy`, `Permissions-Policy`; [10 §15](./10_AUTHORIZATION_SECURITY.md)).
> The session gate is a Client Component (§9.2), and the boundaries are
> `requireUser()` in every route handler and `firestore.rules`.

**Consequence for §9.4's table** (`/login`, `/signup`, `/forgot-password` while signed in → the
role landing route). That behaviour is implemented, in `LoginForm`, using the **role** landing
route from `lib/auth/roles.ts` — not `ROLE_META[role].landing` as §9.4 writes it. `ROLE_META` is
a presentation record (label, icon, tone); the landing route is a separate, security-relevant
table because it must be a total function over `UserRole`, so adding a fifth role is a *type
error* rather than an `undefined` that navigates to `/`.

## A2. `docs/05_FRONTEND_ARCHITECTURE.md` §8.2 — the session context shape changed

**As documented**, `SessionContextValue` has `currentUser`, `initialRole`, `isAllowed`, and
`signOut`. The first and second are placeholders for the mock, and `initialRole` is the Phase 1
seam ("the role to use before the real one loads").

**What was built.** `SessionState` in `components/providers/session-provider.tsx`:

| Field | Type | Why it exists |
| --- | --- | --- |
| `authStatus` | `'initialising' \| 'signed-out' \| 'loading-profile' \| 'signed-in' \| 'error' \| 'unconfigured'` | One discriminated field rather than four booleans, because `isLoading && !user && !error` has three different meanings |
| `firebaseUser` | `{ uid, email, displayName, emailVerified, photoURL } \| null` | The SDK's own record. The only place a `uid` enters the app |
| `user` | `MeResponse['user'] \| null` | The **server-computed** record from `GET /api/me`. The only place a `role` enters the app |
| `profile` | `Profile \| null` | A missing profile is a first-run state, not an error |
| `permissions` | `readonly string[]` | **Server-computed.** Empty while loading, and that is correct |
| `role` | `UserRole \| null` | Narrowed, never widened at a call site |
| `accountStatus` | `AccountStatus \| null` | `status !== 'active'` is a distinct state from signed-out |
| `isAuthenticated` | `boolean` | Exactly `authStatus === 'signed-in'` |
| `isAccountBlocked` | `boolean` | Signed in but refused. Showing the login form would be wrong |
| `error` | `{ code, message } \| null` | A sanitised, renderable sentence |
| `configurationProblem` | `string \| null` | Set when no `.env.local` exists. Explains why nothing works |
| `landingRoute` | `string \| null` | Derived from the role; the redirect target after sign-in |
| `isBusy` | `boolean` | Any auth operation in flight |
| `refreshToken` | `() => Promise<string \| null>` | The **user-triggered** `getIdToken(true)` for a `ROLE_MISMATCH` |
| `refreshMe` | `() => Promise<void>` | Retry a failed `/api/me` |
| `signOut` | `() => Promise<void>` | Audits the event, signs out, clears `cg.*` except `cg.ui` |

Plus two derived hooks:

- `useResolvedSession()` — the same object, guaranteed non-null `role`/`user`, with
  `isAllowed(href)` and `allowedRolesFor(href)` attached. For components **inside** the gate.
  It does not early-return on an unresolved session, because an early return before the
  remaining `useState` calls is a rules-of-hooks violation. Instead it logs a loud
  development-mode warning and renders empty values.
- `useRouteAccess(href)` — for components that need the decision *before* rendering.

**Why `initialRole` is gone.** It was a mock seam. Its removal is the point of the rewrite: a
`defaultRole` prop on a provider is how a demo role survives into a real session. The
`AppProviders` prop changed from `defaultRole` to `defaultTimezone` for the same reason — a
timezone is a real stored value the user can change, not an identity.

## A3. `docs/05_FRONTEND_ARCHITECTURE.md` §7.4 — Zod 4, not Zod 3

§1.1 pins `zod: 3.x`. `DOCUMENTATION_INDEX.md` says Zod 4. The build uses **Zod 4**.

**Amend §1.1** to `zod: 4.x`. The index is the entry point and the later statement, so it wins.
Zod 4 is what `npm i zod` installs today, and pinning to a superseded major is not a technical
decision anyone would defend.

**One API note:** `.strict()` is deprecated in Zod 4 in favour of `z.strictObject()`. It still
works and this build uses it, because `.strict()` on a schema built by `.refine()` (as
`signUpFormSchema` is) has no direct 4.x equivalent. A future cleanup can adopt the newer forms;
there is no behavioural difference for the schemas here.

## A4. `docs/10_AUTHORIZATION_SECURITY.md` §9 — `firestore.rules` needs six additions

The rules file exists and is deny-by-default, but it is not a pure transcription of §9. Six
deviations were forced by the rule language, and each one closes a real gap:

| # | Deviation | Why the documented form does not work |
| --- | --- | --- |
| 1 | `users/{uid}` uses `allow create, update, delete: if false` rather than `allow write: if false` | A `create` has no `resource` to diff against, so a `request.resource.data.keys().hasOnly(...)` guard passes **vacuously on creation**. A client could seed `users/{uid}` with a `role` field. The unconditional `if false` is the only form that holds for all three verbs. |
| 2 | `profiles/{uid}` refuses `notifPrefs.sms == true` and `.whatsapp == true` | [07 §3](./07_DATABASE_SCHEMA.md) stores those fields, but no provider exists (FR-105/106). Refusing at the boundary means a stored `true` can never exist, rather than existing and being silently ignored on every send. |
| 3 | `incidents` create asserts `status == 'new'` with a `get(..., 'new')` default | Without it a client could create an incident already `verified` and skip triage. The `get` default means the rule holds even if the field is absent. |
| 4 | `responderLocations` has no `allow read` | `allow get` and `allow list` cover the point operations; a separate `allow read` would grant `in` queries, which are unbounded and un-rate-limitable. |
| 5 | `evidence` subcollection is `if false` | Evidence is served by a short-lived signed URL from the API after a resource-level check. Direct path access is denied to everyone, which is what stops someone who knows an `incidentId` from constructing the path. |
| 6 | `ratelimits`, `aiRuns`, `analyticsDaily`, `notifications` create are all denied | Rules cannot count requests, so a client-writeable rate-limit bucket or `aiRuns` document would be forgeable. The audit log is the one collection a client may append to, and even that only matters because the server writes it — the client allowance is a convenience, not a grant. |

**Also worth recording:** `match /{document=**} { allow read, write: if false; }` at the end. The
documented §9 does not have a catch-all, and without one a collection added later would be
**open by default** — which is the dangerous direction to fail. The catch-all makes a new
collection closed until someone writes its rule, so the mistake surfaces in development.

## A5. `docs/07_DATABASE_SCHEMA.md` — `AuditAction` needs `auth.blocked`

[10 §3.5](./10_AUTHORIZATION_SECURITY.md)'s account-gate sample writes
`auditLog({ action: 'auth.blocked' })`, but `AuditAction` had no such value. The
consistency report flags this class of gap as **D-16-7**; this is one instance.

**Added** to `types/enums.ts`, with a comment distinguishing it from its two neighbours:

| Action | When |
| --- | --- |
| `auth.login_failed` | A credential problem |
| `auth.blocked` | Refused because the **account** was not active — suspended, disabled, or pending |
| `auth.role_mismatch` | A claim drift: two systems disagree about who this person is |

**Amend §11.5** (or wherever `AuditAction` is enumerated) to add `auth.blocked`.

## A6. `docs/08_API_SPECIFICATION.md` — two decisions the spec did not cover

### 6.1 `PATCH /api/me` with `sms: true` → `422`

[07 §3](./07_DATABASE_SCHEMA.md) stores `notifPrefs.sms` and `.whatsapp`. FR-105/106 require the
switches to be *visible and disabled with a reason* in the UI. The API specification does not say
what happens if a client sends `true`.

**This build rejects it** with a new code, `NOTIFICATION_DISABLED`, and a `details` entry naming
the field. The reasoning: a stored preference the system cannot honour is worse than not offering
it — the setting would look saved and then silently fail on every send, which is the failure mode
a user cannot debug. The UI renders both switches disabled with the server's own sentence as the
reason, so the two can never disagree.

**Add `NOTIFICATION_DISABLED: 422` to the §1.7 catalogue** in [16](./16_ERROR_HANDLING.md).

### 6.2 `GET /api/health` reads no Firestore

[08 §12.3](./08_API_SPECIFICATION.md) and [04 §13.1](./04_UI_UX_DESIGN_SPECIFICATION.md) have the
landing page show a system-status line. If that endpoint reported whether the Admin SDK is
configured, it would be a **reconnaissance endpoint**: it tells an anonymous caller exactly which
pieces of the deployment are missing, which is a short list of things to try next.

So `GET /api/health` reads nothing and reports only whether the **public** config resolved —
which the browser already knows. `status` is `ok` or `degraded`, and the page's copy says
"configuration", not "operational", so it is not read as a service-level claim. The richer
operator endpoint in the spec is admin-gated and does not exist yet.

## A7. `docs/22_USER_ROLES_PERMISSIONS.md` §3 — the matrix is now testable data

§3 is a 61-row table. The build transcribes it to `lib/auth/permissions.ts`, keyed by row
number (`r01_createIncident` … `r61_changeOwnRole`) with four levels: `full`, `scoped`,
`readonly`, `denied`.

Three decisions the table implies but does not state:

1. **`scoped` returns `true` from `can()`.** It means the action exists for this role, narrowed
   by a scope the **server** evaluates. The client never evaluates the scope — it cannot, it does
   not have the document. Returning `false` would render a button the API then accepts.

2. **`readonly` returns `false` from `can()`.** The data is visible with fields removed at
   serialisation time (layer 3, §6); the *action* is not offered. Rendering the button and
   failing on click is worse than not rendering it.

3. **The two hard denials are a frozen `Set`, not just table cells.** `HARD_DENIALS` holds rows
   59 and 61, and `tests/unit/permissions.test.ts` asserts every role is `denied` for both.
   These are the two rows most likely to be removed under deadline pressure — "we need to fix
   the stuck admin account" — and a comment does not fail a test while a set does.

**Also note:** `GET /api/me` returns `permissions[]` as **stable strings**, computed by walking
this matrix server-side. The client does not call `can()` to decide what to render; it reads the
server's list. A client that derived its own permissions would be deriving them from a role it
holds, which is the vulnerability [22 §2](./22_USER_ROLES_PERMISSIONS.md) exists to prevent.

## A8. `docs/24_THREAT_MODEL_SECURITY.md` — two residual risks are now closed

| Risk | Before | After |
| --- | --- | --- |
| **TB1 — role self-escalation** | Mitigated by API design | **Closed by construction.** Four independent blocks: no `role` field in any request schema, `selfServiceRoleSchema` is a `citizen` literal, no role in browser storage or the URL (mechanically scanned), and `users` is `allow create, update, delete: if false` in the rules. Removing any one leaves three. |
| **TB3 — role elevation via token claim** | Documented as a claim-drift risk | **Detected, not just mitigated.** `requireUser()` step 6 reads the authoritative role from Firestore and step 7 compares it to the claim. A mismatch is `403 ROLE_MISMATCH` **plus** an `auditLogs` row. An admin who has just been demoted loses admin immediately, not at token expiry. |
| **TB4 — account enumeration** | "we never call a server route that reveals existence" | **Closed and testable.** `auth/invalid-credential` maps to one neutral sentence for both a wrong password and an unknown address. `POST /api/auth/event` returns `200 { ok: true }` unconditionally and performs no lookup. `resetPassword()` swallows `auth/user-not-found`. |

**One risk the implementation deliberately did NOT take on:** the Phase 2 brief's example message
"No account was found with this email" is **not implemented**, and its absence is a decision.
Implementing it would turn the login form into an account-existence oracle, which is both an
enumeration vulnerability and a privacy leak in a system where a member may reasonably assume
an incident reporter's address is not public. The code comment at `INVALID_CREDENTIAL` in
`lib/firebase/auth.ts` records it.

## A9. `docs/21_ENVIRONMENT_VARIABLES.md` — three variables this phase introduced

| Variable | Purpose | Why it is safe |
| --- | --- | --- |
| `REAUTH_WINDOW_SEC` | How old an `auth_time` may be for a privileged action ([10 §3.6](./10_AUTHORIZATION_SECURITY.md)) | A number. Default 300 |
| `NEXT_PUBLIC_FIREBASE_USE_EMULATORS` | Points every SDK at the local emulator suite | A boolean. The emulator is **optional** — Phase 2's unit tests deliberately avoid it so `npm test` needs no Java runtime |
| `FIREBASE_AUTH_PROVIDERS` | Documents which providers are enabled in the console | A comma list. It is **documentation, not a switch** — the SDK reads the project's auth config, not this variable |

**Note on the emulator.** The Auth emulator accepts *any* password for an existing account and
*any* 6+ character password for a new one. A passing emulator password test is **not** evidence
about password strength. This is recorded in `.env.example` and
[29 Demo Scenario](./29_DEMO_SCENARIO.md) should carry it too.

## A10. `docs/30_DEVELOPMENT_PHASE_PLAN.md` — cut list applied

§5.9 lists a Phase 2 cut list. Two items were cut, and both were cut for the same reason: they
require a route or a screen that only Phase 5 needs.

| Cut | Consequence |
| --- | --- |
| The role-change API route (`PATCH /api/admin/users/{uid}/role`) | Roles are granted by an Admin SDK script. The **guards** it would use — `assertNotSelfRoleChange`, `assertReasonPresent`, `assertRole` — all exist and are tested; only the route is missing |
| `validators/admin.ts` | The two-step confirm dialog and the reason field exist in the admin screens. The Zod schema for the request body does not, because there is no request |

**Not cut, and specifically in scope:** the claim-mirror write after a role change. It is
deferred *with* the role-change route, since there is nothing to mirror.

## 5.11 Divergences from the plan, and why

### 1. There is no authentication in `middleware.ts`, and no `lib/server/require-session.ts`

**The plan** (§5.2 tasks 2.3–2.4) and [05 §9.1](./05_FRONTEND_ARCHITECTURE.md)
describe an Edge middleware that reads a session cookie and redirects, plus
`requireSession()` in a Server Component.

**What was built instead:** `RequireSession`, a Client Component gate.

**Why.** [10 §12.1](./10_AUTHORIZATION_SECURITY.md) and §12.3 state that this
product attaches **no session cookie** — every API call carries
`Authorization: Bearer <Firebase ID token>`. There is nothing at the Edge to
read. The authoritative role lives in `users/{uid}.role`, and the Firestore Admin
SDK does not run on the Edge runtime, so even reading the role there is
impossible. [05 §9.2](./05_FRONTEND_ARCHITECTURE.md) already documents this: the
middleware "is a redirect convenience only. It is never a security control."

So the plan and [10](./10_AUTHORIZATION_SECURITY.md) contradict each other. The
implementation follows §9.2, because inventing a cookie to satisfy the §9.1
sketch would create a security control that *looks* like one — worse than none,
since a team would then believe the Edge protected the routes.

A Server Component `requireSession()` has the same problem for a different
reason: the session is in `localStorage`/`indexedDB`, which a server cannot read.
Making it work would require moving the token into a cookie — the exact
architectural change §12.3 rejects.

`middleware.ts` exists and sets the response headers from
[10 §15](./10_AUTHORIZATION_SECURITY.md) (CSP with a per-request nonce,
`X-Frame-Options`, HSTS, `Referrer-Policy`, `Permissions-Policy`).

**The boundaries that DO exist**, all implemented and all tested:
1. `requireUser()` on every API route — the real boundary.
2. `firestore.rules` — deny-by-default for every client-SDK read and write.
3. `RequireSession` — the redirect convenience, honestly labelled as such.

### 2. `auditLogInTransaction` takes the Firestore handle

`Transaction.collection()` is not on the public `Transaction` type in
`firebase-admin`, so the helper takes `(tx, db, input)`. Making `db` explicit is
the point: the alternative is reaching for a module-level `getAdminDb()` inside
the helper, which would quietly turn a transactional write into a direct one —
the exact bug the function exists to prevent.

### 3. `lib/api/schemas.ts` is folded into the endpoint functions

[05 §7.1](./05_FRONTEND_ARCHITECTURE.md) lists a separate `schemas.ts`. Phase 2
has four endpoints, so the schemas sit next to the function that uses them.
Splitting them would mean two files to change per endpoint. This is a
reversible formatting choice, not an architectural one; Phase 3 should split it
once the endpoint count justifies it.

### 4. Zod 4, not Zod 3

[05 §1.1](./05_FRONTEND_ARCHITECTURE.md) pins `zod: 3.x`;
`DOCUMENTATION_INDEX.md` says Zod 4. This build uses **Zod 4** (the current
major). `DOCUMENTATION_INDEX.md` is the entry point and the later statement, so
it wins — but [05 §1.1](./05_FRONTEND_ARCHITECTURE.md) should be amended.

### 5. `auth.blocked` added to `AuditAction`

[10 §3.5](./10_AUTHORIZATION_SECURITY.md)'s account gate writes
`auditLog({ action: 'auth.blocked' })`, but the `AuditAction` enum had no such
value — the documentation's own consistency report flags this class of gap as
D-16-7. Added to `types/enums.ts` with a comment. **`docs/07 §11.5` needs the
same amendment.**

### 6. `PATCH /api/me` refuses `sms: true` and `whatsapp: true`

[07 §3](./07_DATABASE_SCHEMA.md) stores `notifPrefs.sms` and `.whatsapp`, and
[01 FR-105/FR-106](./01_PRODUCT_REQUIREMENTS_DOCUMENT.md) require the switches to
be visible and disabled with a reason. It does not say what the API does if a
client sends `true`.

This build **rejects with `422 NOTIFICATION_DISABLED`**, because recording a
preference the system can never honour is worse than not offering it: the
setting would look saved and silently fail on every send. The UI renders both
switches disabled with the server's sentence as the reason, so the two agree.

## 5.13 Two bugs the runtime check found

`npm run verify` was green and the tests passed while **every API route returned 500**
on an unconfigured deployment. The unit suite could not see either bug, and both
were found by actually starting the server and calling the endpoints. Recording
them because the failure mode is instructive: *the gate passing is not the same as
the behaviour being right.*

### Bug 1 — the logger could prevent logging

`createLogger()` read `LOG_LEVEL` through `getServerEnv()`, which **throws** when
`FIREBASE_PROJECT_ID` is missing. It is called at the top of every route handler,
**outside** the `try` in `withRequest`, so the throw escaped the envelope handler
entirely:

```
GET /api/health  ->  500   (empty body)
```

on the one endpoint whose entire job is to answer when the deployment is
unconfigured.

**Fixed structurally**, not with a special case: `createLogger` now reads
`LOG_LEVEL` directly and falls back to `info`. *A logger must not be able to
prevent logging* — and a level is not a secret, so there was never a reason to
route it through the secret accessor.

### Bug 2 — the configuration check ran after authentication

The Admin-SDK precondition was evaluated **after** the handler. An unconfigured
deployment therefore reached `getAdminDb()`, got a bare `Error` out of the SDK
bootstrap, and answered `500 INTERNAL` with *"Something went wrong. Nothing was
changed."* — the wrong status, and a message that says nothing about the cause.

**Fixed two ways**: the precondition moved to the **first** statement in
`withRequest`, and `getAdminServices()` now throws a typed
`AppError { code: 'SERVICE_UNAVAILABLE' }` rather than a bare `Error`, so any
future path that reaches it also gets 503.

**The result now**, with no `.env.local`:

| Request | Status | Body |
| --- | --- | --- |
| `GET /api/health` | **200** | `{ status: "degraded", version: "0.1.0-phase2" }` |
| `GET /api/me` | **503** | `SERVICE_UNAVAILABLE` + the three variable names |
| `PATCH /api/me` | **503** | same |
| `POST /api/auth/event` | **503** | same |
| `POST /api/me/bootstrap` | **503** | same |

`/api/health` opts out of the precondition, because a liveness endpoint that
503s because a secret is missing is a false negative on the one route that must
always answer — and it would page an operator for the exact condition it exists
to describe.

Both are pinned by `tests/unit/unconfigured-deployment.test.ts` (the accessor
contract and the status-code mapping). The HTTP-level behaviour is documented in
that file as a manual check, because this suite starts no server process.

## 5.14 Manual checks still required

These need a real Firebase project and a browser, so they are not automated.
Run them in order.

```
1. cp .env.example .env.local     # fill in the Firebase values
2. npm run dev
3. Sign up as a citizen          # role must be `citizen`; check /admin/users
4. Devtools → localStorage.cg.role = "admin" → reload
   → still a citizen; /admin renders the 403 state in place
5. Devtools console:
     import { doc, setDoc, getDoc } from 'firebase/firestore'
     setDoc(doc(db(), 'users', '<your uid>'), { role: 'admin' })
   → PERMISSION_DENIED. This is the fourth and strongest block.
6. Sign in as a dispatcher        → /dashboard, with a dispatcher nav
7. Sign in as an admin            → /admin, and the full nav
8. Sign out                        → every cg.* key except cg.ui is gone;
                                       /dashboard redirects to /login?next=/dashboard
9. Sign in again                   → lands back on /dashboard
10. Suspend a user as admin        → that user sees "This account is not
                                      available" with a sign-out action
11. npm test && npm run security:check
```

## 5.15 Phase 2 → Phase 3 seam

Phase 3 needs to know four things.

1. **The token seam is `setTokenProvider`.** `lib/api/client.ts` never imports
   Firebase. `SessionProvider` registers the provider. A Phase 3 API client only
   needs `apiFetch` and its own Zod schema.
2. **`requireUser(options)` is the whole guard.** Add
   `action: 'incident.create'` for the re-auth check and
   `assertRole(user, ['citizen','responder','dispatcher','admin'])` — the
   per-collection visibility rule is `assertResourceAccess`, which throws **404**.
3. **`withRequest` is the only route wrapper.** It already does request-id,
   same-origin, Zod-before-I/O, auth, the Admin precondition, and the error
   envelope. A new route declares options and a handler.
4. **Phase 3 does NOT need a session migration.** The types are unchanged; only
   the data source changes. `lib/mock-data` stays for incidents, maps, and
   analytics; only `users` and `profiles` are real.

**Two open decisions that Phase 3 inherits:** D-01 (Vercel max function duration
vs the Gemini timeout) and D-02 (the Firestore region, which is irreversible).
Both must be answered before the first deploy.

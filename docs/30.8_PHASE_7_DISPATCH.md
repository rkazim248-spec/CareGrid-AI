# 30.8 — Phase 7: Responder Management & Dispatch

**Status:** complete, with one declared gap (§10)
**Precedence:** T0 anchors outrank the brief. Every identifier and rule below is
taken from `docs/`; the brief's proposals are recorded where they differed and the
document won.

---

## 1. What this phase is

A controlled human-in-the-loop dispatch workflow:

```
Incident → suitable responders → dispatcher reviews → dispatcher assigns
        → responder accepts or declines → en route → on scene → resolved
        → reporter sees the status change
```

with an append-only status history and an operational audit log, and **no path by
which the system assigns anyone on its own**.

The pure policy is two modules in `lib/dispatch/`. Everything that touches
Firestore is in `services/dispatch/`. Nothing in either imports the other.

## 2. Where the documentation overruled the brief

The brief's Phase 7 section proposes several vocabularies. In every case the
documentation already specified one, Phase 3 had already implemented it, and a
second one would have meant a second code path and a second set of queries. The
documented set stands in all six.

| # | Brief proposes | `docs/` specifies | Phase 3 built | Decision |
| --- | --- | --- | --- | --- |
| 2.1 | Responder status `available / busy / en_route / on_scene / offline / unavailable` | `docs/07 §7.1`: `available \| busy \| offline` (FR-061) | `RESPONDER_STATUSES` | **3 values.** See §2.2 |
| 2.2 | Dispatch status `assigned / accepted / rejected / en_route / on_scene / completed / cancelled` | `docs/07 §8`: `active \| accepted \| withdrawn \| completed \| expired` | `DISPATCH_STATUSES` | **5 values.** See §2.3 |
| 2.3 | Capabilities `medical / fire / rescue / traffic_control / security / flood_response / heatwave_response / general_aid` | `docs/07 §4.4`: capabilities are `resourceId` values from the catalogue | `RESOURCE_CATALOGUE` | **Catalogue ids**, e.g. `res_ambulance`. See §2.4 |
| 2.4 | Model `currentLocation`, `availability`, `serviceArea`, `maxConcurrentIncidents` | `docs/07 §7.1`: `lastLocationAt`, `status`, `serviceRadiusM`, `maxConcurrentIncidents` | `Responder` | **As documented.** See §2.5 |
| 2.5 | `id`, `name`, `createdAt`, `updatedAt` | `docs/07 §7.1`: `uid`, `displayName`, `verification`, `capabilities`, … | `Responder` | **No new model.** See §2.6 |
| 2.6 | Service `findAvailableResponders()` | `docs/08 §3.6`: the candidate list is part of the dispatch endpoint's read side | — | Implemented, plus a `GET` route |

### 2.2 Why a responder holding a dispatch is `busy`, not `assigned`

`docs/07 §7.1` defines three statuses. Inventing `assigned` would break every query
filtering `status in ['available', 'busy']` — including the candidate query this
phase depends on — and `en_route` belongs to the **incident** lifecycle, not to a
responder's availability. Where a responder is in the operational workflow is
recorded on `incidents.status` and `dispatches.status`, which is where `docs/07 §4`
and `docs/07 §8` put it.

The consequence worth stating: a responder can hold up to
`maxConcurrentIncidents` (default 1) dispatches and be `busy` for all of them, so
`busy` means "not free", not "driving".

### 2.3 Mapping the brief's dispatch statuses onto the documented five

| Brief | `docs/07 §8` | Note |
| --- | --- | --- |
| `assigned` | `active` | Awaiting a response. Expiry after `DISPATCH_EXPIRES_SEC`. |
| `accepted` | `accepted` | The subject responder accepted. |
| `rejected` | `withdrawn` + `withdrawnReason` | The status does not distinguish a decline from a cancellation; the reason does. |
| `en_route`, `on_scene` | — | **Not dispatch states.** They are `IncidentStatus` values (`docs/07 §4.3`). |
| `completed` | `completed` | Set when the incident is resolved. |
| `cancelled` | `withdrawn` | As above. |

### 2.4 Capabilities are `resourceId`s

`docs/07 §4.4`: `requiredResources[].resourceId` values, and `docs/07 §7.1`:
`capabilities` are "`resourceId` values from the catalogue". The catalogue is
`config/resources.ts` (14 entries, `res_ambulance`, `res_fire_engine`,
`res_water_rescue`, …). The brief's eight labels have no catalogue entry and
would not have matched anything the AI triage emits.

`capabilityMatch` is `docs/07 §8`'s definition verbatim: all required resources
present in `capabilities`. When an incident requires nothing, it is `true` — the
dispatch was still a dispatcher's decision, and a record claiming the capabilities
did not match would be a false criticism of it.

### 2.5 `serviceRadiusM`, not `serviceArea`

`docs/07 §7.1`: "`serviceRadiusM` | `number` | default 5000, range 500-50000
(FR-062)". A `serviceArea` string would be free text that cannot be compared
against a coordinate.

**The radius is soft.** A responder beyond their own radius is still assignable,
and the panel says so. `docs/07 §7.1` makes it an operational fact, and refusing
the assignment would remove that judgement from the person who has it. It is
surfaced as a factor and sorted, and the buttons stay enabled.

### 2.6 No second responder model

`types/domain.ts`'s `Responder` already carried `uid`, `displayName`, `status`,
`verification`, `capabilities`, `serviceRadiusM`, `activeIncidentCount`,
`maxConcurrentIncidents`, `certifications`, `stats`. Nothing was added to it and no
parallel type was created.

## 3. `lib/dispatch/transitions.ts` — the one place a transition is decided

`docs/07 §4.3`'s matrix, transcribed **cell by cell including the dashes**. Pure:
no Firestore, no clock, no randomness. A transition table is policy, and policy is
the one thing here that must be testable without a database.

```
lib/dispatch/transitions.ts
  evaluateIncidentTransition(from, to, ctx) → { allowed } | { allowed, reason }
  canTransitionIncidentStatus(...)             → boolean
  allowedIncidentTransitions(from, ctx)        → IncidentStatus[]
  checkTransitionPrerequisites(to, prereqs)    → { ok } | { ok, code }
  canTransitionDispatchStatus(from, to, ctx)   → boolean
  allowedDispatchTransitions(from, ctx)        → DispatchStatus[]
```

### 3.1 The transcription had to be redone

The first attempt was **wrong in four cells**. `docs/07 §4.3` is a markdown table
whose first cell is a row label, so a `split('|')` shifts every column by one and
produces a table that looks plausible and is wrong. The corrections:

| Cell | First reading | Actual |
| --- | --- | --- |
| `new → merged` | `dispatcher, admin` | **denied** — a dash |
| `new → false_alarm` | denied | **`dispatcher`** |
| `verified → assigned` | denied | **`dispatcher, admin`** |
| `assigned → closed` | denied | **`dispatcher`** |
| `on_scene → cancelled` | `dispatcher, admin` | **denied** — a dash |

The whole-grid transcription is now verified by re-parsing the source table with a
script that prints one cell per line, and the corrected matrix is asserted cell by
cell in `tests/unit/dispatch/transitions.test.ts`.

### 3.2 Three doc-to-code reconciliations, each recorded in the source

1. **`admin` is admitted wherever `dispatcher` is.** The matrix never says so, but
   `lib/auth/permissions.ts` gives `admin` `full` on every operational capability
   including `r29_assignResponder`, and an admin who could not mark an incident
   `on_scene` could not supervise a dispatch they were entitled to create. Done in
   ONE function (`cellGrantsDispatcherRole`) rather than in 30 cells.

2. **`assigned → on_scene` also admits a dispatcher.** Its cell reads "responder
   (documented jump, flagged)" — the only cell in that row omitting a dispatcher,
   while its neighbours `en_route` and `resolved` both name one. Read literally, a
   dispatcher could go `assigned → resolved` while being forbidden from recording
   the `on_scene` step. That is a contradiction, not a policy.
   Exported as `DOCUMENTED_DEVIATIONS` and asserted by a test.

3. **The entire `merged` column is denied, so `merged` is unreachable via
   `PATCH /status`.** `docs/07 §4.3` puts a dash in all eleven. The status is real
   and is written by a dedicated merge operation, which Phase 6 deliberately did not
   build (FR-048: two incidents 500 m apart are never auto-merged). So
   `allowedIncidentTransitions` never offers a `merged` button, because the API
   would refuse it.

### 3.3 The AI is allowed exactly one transition

`docs/07 §4.3`: "This is the only lifecycle transition the AI can cause (FR-020)"
— and never on the AI-failure path. `system (ai)` appears in **exactly one** cell
of the whole grid, asserted by a test and by security check 25. brief §3's
human-in-the-loop rule reduces to that one cell.

The sentinel requires **both** `uid === 'system'` and `role === 'system'`. An
admin with the sentinel uid is refused the AI cell and may still triage through the
`dispatcher`/`admin` cell beside it — conflating the two would make the audit log
claim a human action was an AI one.

### 3.4 Refusals carry an instruction, not a shrug

`evaluateIncidentTransition` returns a `reason`, because three refusals tell the
caller what to do: `requires_active_dispatch`, `requires_live_assignee`,
`system_only`. A bare `false` would let a caller produce an `assigned` incident
with no dispatch — the exact inconsistency FR-053 exists to prevent.

### 3.5 Repeats are no-ops

`docs/08 §3.8`: "Repeating the same transition returns `200` with `meta.noop:
true`". Checked **before** the terminal test, so `merged → merged` is a noop like
any other repeat, and `docs/08`'s `allowedNext` comes back on the way.

## 4. `lib/dispatch/candidates.ts` — explainable ranking, not a score

brief §12 forbids "97% best responder" without a documented, validated model. So
this module produces a **lexicographic order** over named factors, and `rank` is an
**ordinal** (1st, 2nd) rather than a confidence — a UI cannot render it as a
percentage even by accident.

| Order | Factor | Why there |
| --- | --- | --- |
| 1 | `isAssignable` | Unverified, offline or at capacity is not a candidate, whatever else is true. |
| 2 | `staleLocation` | US-022 AC2: a 40-minute-old fix is worse than a current one at a greater distance. **Sorted last, not filtered** — a dispatcher may know the person parked nearby. |
| 3 | `capabilityMatch` | A fire responder for a road accident is not usable. |
| 4 | `status` | `available` before `busy`. |
| 5 | `activeIncidentCount` | Capacity pressure among equals. |
| 6 | `distanceM` | **Last.** |
| 7 | `uid` | A total order, so two identical profiles do not shuffle between renders. |

**Distance last is the decision that matters.** A distance-first sort puts a 200 m
away responder with no relevant skill above a 3 km paramedic.

### 4.1 `factors` is the explainability requirement, as data

Every candidate carries its reasons as first-class data, **including the
blockers**. A dispatcher looking at a responder who is not assignable needs to
know it is verification and not a query failure; "not assignable" with no reason
is indistinguishable from a bug.

### 4.2 No ETA, anywhere

brief §30: "Do not claim travel time unless a real routing API has been
implemented. Distance is not the same than ETA." There is no routing provider in
this project. `docs/07 §8` has an `etaSec` field and Phase 3 typed it; it is
written `null` and never computed. A test walks the whole candidate object
asserting no key name implies a time, and asserts no factor `detail` claims one —
the text is what a dispatcher reads, so the text is what the assertion is about.

Distance reuses Phase 6's `haversineMetersRounded`. No second implementation.

## 5. `services/dispatch/assign.ts` — the race

brief §15:

```
Dispatcher A                         Dispatcher B
    reads responder X: available        reads responder X: available
              |                                    |
              v                                    v
        assign(X) ---> [ TRANSACTION ] <--- assign(X)
```

### 5.1 The subtle half: the transaction must **write** the responder

Firestore only guarantees conflict detection for documents a transaction both
reads **and writes**. A transaction that merely read `responders/{uid}` would
still let both dispatchers commit. So the assignment writes
`activeIncidentCount: activeCount + 1` — that write is the contention point.
Remove it and the guards still pass their unit tests and still race in production.

Security check 27 asserts both halves, scoped to the `responderRef` write rather
than the function body (§8.2).

### 5.2 Everything is re-read inside the transaction

Nothing but an id and a note comes from the caller. In particular the responder's
`status` and `verification` are re-read, never accepted from the panel: a
dispatcher clicking a row rendered thirty seconds ago may be assigning someone who
has since gone offline, and the panel cannot be the thing that authorises the
write.

The guards, in order, all inside the transaction:

1. Incident exists, not soft-deleted, and `evaluateIncidentTransition(current,
   'assigned', …)` allows it.
2. Responder `verification === 'verified'` (FR-064).
3. Responder `status` is `available` or `busy`.
4. `activeIncidentCount < maxConcurrentIncidents`.
5. Assigning the responder who is **already** assigned is a **no-op**, not a 409 —
   brief §22's confirmation dialog exists to make an accidental single click
   harmless, and punishing the double click would undo that.

### 5.3 `assigneeUid` — the field the rules key on

`docs/07 §4`: "`assigneeUid` | current assigned responder; **denormalised from the
active dispatch**". Phase 3's `firestore.rules` already grants a responder access
to an incident when `resource.data.assigneeUid == request.auth.uid`.

**Without writing it, the whole workflow is unreachable from the client** — the
dispatch exists in the database and the assignee cannot read their own incident.
It is written in the same transaction as the dispatch, together with the
denormalised `assignee: AssigneeSummary`.

And it is **cleared on decline**, which is a security property: leaving it set keeps
granting read access to a responder who just walked away, or whose dispatch a
dispatcher cancelled.

### 5.4 One transaction, seven writes

1. the dispatch (`merge: false`)
2. the responder's counters — **the contention point**
3. the incident: `status`, `assigneeUid`, `assignee`
4. the previous dispatch closed as `withdrawn` (reason `"reassigned"`) — brief §32:
   the old record is **preserved**, never overwritten
5. the previous responder's counter decremented, **floored at zero** (an
   `inc(-1)` cannot be floored, and a negative counter makes a responder
   permanently assignable past their limit)
6. the `statusHistory` event (FR-052)
7. the `auditLogs` row

Steps 4–7 are all in the same transaction as the dispatch. A dispatch whose audit
line could fail independently is the worst gap this system could have. The
accepted cost — a retried transaction writes two audit rows with different ids —
is documented on `auditLogInTransaction`, with the instruction that consumers key
on `action + entityId + createdAt` rather than `logId`.

Nothing throws after the guards, so a refusal cannot leave a partial write.

## 6. `services/dispatch/lifecycle.ts` — accept, decline, cancel, transition

`respondToDispatch` and `transitionIncident` share the shape described in the file
header: verify the actor against the **resource**; ask the pure table; re-read
inside one transaction; write state + history + audit together; notify after.

### 6.1 Only the subject may accept

`canTransitionDispatchStatus` refuses a dispatcher accepting on a responder's
behalf. `accepted` exists to prove the responder is available and willing; a
dispatcher accepting for them makes the field a fact about the dispatcher.

### 6.2 Expiry is the clock's decision, not a person's

`active → expired` is permitted for `role === 'system'` only. A dispatcher cannot
expire a dispatch manually, and `withdrawn` does not consult `isExpired` — letting
a dispatcher withdraw an expired one would rewrite the reason a responder never
picked it up.

An expired assignment cannot be **accepted** either: a responder is told to ask for
a reassignment rather than being sent to an incident a dispatcher has already been
told nobody accepted.

### 6.3 A decline returns the incident to the dispatcher

brief §18: "Do not automatically assign a replacement without dispatcher
confirmation." A decline closes the dispatch, releases the responder's capacity,
moves the incident back to `triaged` (a state a dispatcher can act on, and
reachable from `assigned` for a dispatcher per `docs/07 §4.3`), clears
`assigneeUid`, and notifies the dispatcher. **There is no "find someone else" step
anywhere in this file**, and that absence is the human-in-the-loop rule.

### 6.4 The documented jump is recorded, not refused

`docs/07 §4.3` marks `assigned → on_scene` "documented jump, flagged". The
transition is allowed — a responder who arrives without opening the app has told us
something real, and refusing it would make them leave the app and phone instead —
and `statusHistory.metadata.skippedEnRoute` records which step was skipped.

### 6.5 Resolution completes the dispatch

When an incident reaches `resolved` and its live dispatch is `accepted`, the
dispatch is set to `completed` in the same transaction. Leaving a `completed`
incident with an `accepted` dispatch would hold the responder's capacity for an
incident that no longer exists.

## 7. Audit, history, notifications

### 7.1 `auditLogs` — an allow-list, not a deny-list

`docs/07 §11.5`: "whitelisted fields only - **never** raw PII or evidence URLs".

The distinction decides whether a future field leaks. A deny-list lets the next
`phoneHash` or `location` field through unnoticed; an allow-list means a new field
is invisible until someone deliberately adds it. So `buildAuditDiff` copies only
named keys, and `assertAuditSafe` **throws** on a whitelist that names a forbidden
one — throwing, because a silent filter would mean a call site asked to log
`phone`, got no `phone`, and had no idea.

Stated honestly: the whitelist is the primary control; `FORBIDDEN_AUDIT_FIELDS` is
a backstop on the one input a developer controls directly. A name not in the
deny-list but whitelisted anyway **does** get written. That is why a forbidden
name is a code-review question, not something a list can settle.

A non-scalar value is **dropped, not stringified** — `JSON.stringify` of an
evidence array would put a storage path in an audit row.

`AUDIT_ACTIONS` already contained every action Phase 7 needs. No action was added
to the enum, because an action outside it is one no compliance review can filter
for.

### 7.2 `statusHistory` — append-only in code, not just in the rules

`docs/07 §6`: "Append-only. Never updated, never deleted." There is no update
function and no delete function. A correction is recorded as a **new** event.

`metadata` is a **scalar union**, so a coordinate is not representable without a
cast — the most likely leak is a caller helpfully passing `geo` into a "small
metadata" map, and with `Record<string, unknown>` that compiles.

A reason is required for `false_alarm`, `cancelled` and unassign/merge
(`docs/07 §6`), enforced in the **builder** so a caller cannot skip it. `"   "` is
not a reason.

### 7.3 Notifications — stored, not pushed, and they may not overclaim

`docs/13 §3.3`: an in-app notification is a Firestore document; the client's
listener is the transport. **No FCM registration, no device token, no push call** —
their absence is the design. A responder with the app closed sees the assignment
when they next open it.

**FR-107: a notification failure must never fail the request.** `notifyInApp` is
per-recipient with its own catch, and the routes notify **after** the commit: a
notification inside the transaction would roll back with it, and one written before
the commit would tell a responder about an assignment that then failed.

**brief §28 — no overclaim.** `FORBIDDEN_NOTIFICATION_CLAIMS` is a list of
sentences this module refuses to write, asserted against every string the phase
can produce. The subtler rule: **acceptance is not reported as departure.**
Acceptance and setting off are different events, and only the second would support
"on the way".

The dedupe key includes `incidentRef` **and** `actor.uid`, so "assign Ahmed", then
"assign Sara", then a **retry** of "assign Ahmed" correctly notifies Ahmed twice
and Sara once. A key of `type + incidentId` would swallow the second notification
and a dispatcher would wait for a responder who was never told.

Recipients follow `docs/07 §10.2` narrowly: an acceptance notifies **the assigning
dispatcher**, not "all dispatchers" — this is one person's answer, and a broadcast
would page every dispatcher in the city.

### 8.1 Four checks would have failed on a CORRECT implementation

`notify.ts` necessarily **contains** every phrase it refuses (that is
`FORBIDDEN_NOTIFICATION_CLAIMS`), and `config/dispatch.ts` explains in a comment
why it has no env vars. Checking for those strings without stripping comments
fails on correct code — and the fix a developer reaches for is to delete the list
of forbidden phrases, removing the control.

So every source is passed through `codeOnly()` first, and the one check whose
subject *is* a declaration of forbidden strings also uses `excludes()`.

### 8.2 Two checks were passing for the wrong reason, and the mutations found them

Both with the same shape — a whole-file search for a string that appears somewhere
else too:

- **27** looked for `activeIncidentCount: activeCount + 1` anywhere in
  `assignResponder`, and found it in the **audit diff** as well as the write.
  Deleting the write left the check green.
- **37** looked for `reason: reason.optional()` anywhere in the validators, and
  found it in the **status** schema as well as the reject one. Tightening the
  reject schema left the check green.

Both are now scoped to one declaration via `blockAfter()`. And a third ordering bug:
`codeOnly()` strips the `/* ====` banner `blockAfter()` cuts on, so check 37 was
scoping an empty string and passing for no reason at all.

**19 mutations, 19 caught.** Two mutations were themselves invalid — one appended
a second `reason:` key beside the optional one, so Zod was still optional and the
check was right to stay green; the other renamed a symbol to one that still
*contains* the marker substring, which is why the scope marker now anchors on
` =`.

## 10. What is NOT built

### 10.1 No UI

**There is no dispatcher candidate panel, no responder dashboard, no responder
management screen, no citizen status tracker, and no `LocationPicker`/
`IncidentMap` rendering.** The API, the pure ranking and the explainability
contract exist and are tested; nothing renders them.

This is a real gap against brief §7, §13, §21, §23, §29 and §35, and it is the
largest one. It was left out rather than half-built because the brief's UI
requirements are inseparable from the map rendering Phase 6 also did not build, and
a candidate panel that cannot show a map or a distance is not the panel brief §21
describes. Shipping `MarkerSpec` without a renderer (Phase 6's decision) plus a
candidate list without a map would have produced two half-features that look
complete in a file listing.

The pieces a renderer needs are all present and tested: `rankCandidates` with its
`factors`, `formatDistance`, `criticalIncidentHeading`,
`NO_RESPONDER_AVAILABLE_COPY`, `buildMarkerSpec` (Phase 6), and the four routes.

### 10.2 Everything else

| Gap | Why |
| --- | --- |
| No realtime listener | `docs/11`'s listener budget (`MAX_REALTIME_LISTENERS = 8`) and a Firestore client are not wired to the new collections. `responders` and `dispatches` reads are one-shot per request. brief §26's "dispatcher sees acceptance" works only on refresh. |
| No `responderLocations` client write | `firestore.rules` already permits a responder to write their own location (`docs/07 §7.2`, FR-066), and Phase 6's `use-geolocation` captures a position — but nothing calls it for a responder, and the rate limiter for it (`docs/10 §11`) is not implemented. |
| No `POST /api/incidents` | Carried from Phase 5 §6.1. No incident is created, so no dispatch can be exercised end to end. |
| No expiry sweep | `DISPATCH_SWEEP_INTERVAL_SEC` is defined and `active → expired` is permitted for the system only, but no scheduled job runs. An unaccepted dispatch stays `active` until someone acts. |
| No `firestore.indexes.json` | The candidate query needs composite index
`status ASC, verification ASC, lastLocationAt DESC` (`docs/07 §7.1`) and the live-dispatch lookup needs `incidentId ASC, status ASC` (`docs/07 §8`). Neither is deployed, so **no Firestore read in this phase has been executed.** |
| No `POST /api/dispatches/:id/claim` | `self_claimed` mode is accepted by `assignResponder` and `r31_claimOpenDispatch` exists, but the route is not written. |
| No responder self-service routes | `r34_setOwnAvailability` exists and `firestore.rules` permits the write; there is no `PATCH /api/responders/me`. |
| No resolution-note capture in a UI | The `ResolutionRecord` is stored and validated; nothing collects it. |
| `merged` unreachable | By design (§3.2), pending a merge endpoint. |
| No admin verification UI | `r38_verifyRejectResponder` and `responders.verification` exist; the route is not written. |

### 11.1 The one number a later phase should not re-derive

`activeIncidentCount` is a **denormalised counter maintained transactionally**, not
a computed fact. Any feature that wants "how many incidents is this responder on"
must read it, not count dispatches — and must not increment it outside
`services/dispatch/assign.ts`, or the capacity check in §5.2 stops meaning
anything.

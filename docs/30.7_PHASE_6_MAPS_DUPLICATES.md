## 2. Six places the documentation overruled the brief

### 2.1 The time window is 6 hours, not 24

brief §22 says `DUPLICATE_LOOKBACK_HOURS=24`. **`docs/01` FR-040 row 9 says "500 m + 6 h", and `docs/07 §9.5` states `duplicateTimeWindowMin: 360`.** DEC-02 records 6 h as the accepted decision.

The brief's 24 is given as an example ("For example: `DUPLICATE_LOOKBACK_HOURS=24`"), and the very next sentence says "If the documentation specifies a different value, follow it." So this is the brief deferring to `docs/01`, not a conflict. **Implemented as 6, with the divergence recorded in `.env.example`** so an operator reading the brief's value finds out why it differs.

### 2.2 The source enum is `gps | manual_pin | address_text | none`

brief §8 proposes `device | map_selection | manual | existing_incident`. `docs/12 §2.1` specifies the four above, and **Phase 3 already implemented them** in `types/enums.ts`. `existing_incident` has no counterpart in the specification at all.

No change was needed: the code already matched the specification. The brief's enum would have meant rewriting Phase 3's type and every consumer.

### 2.3 The field is `geo`, not `location`

brief §15 proposes `location: { latitude, longitude, accuracyMeters, source, address, capturedAt }`. `docs/07 §4.1` and `docs/12 §2.3` specify `geo: { lat, lng, accuracyM, accuracyGrade, source, placeName }`, and `types/domain.ts` implements it.

Two differences that matter beyond naming:

- **`accuracyGrade` is not a client input.** `docs/12 §2.2`: grading is "a communication device" whose value is that it was *derived*. A client claiming `high` with a 900 m fix would make the marker solid and the warning vanish. The schema refuses it.
- **`capturedAt` is not a client input** either. The browser may return a cached fix up to 30 s old (`maximumAge`), and a device clock can be wrong by years. The server stamps its own.

### 2.4 `geoCells` is 9, and `docs/07`'s "exactly 10" is an arithmetic error

`docs/07 §9.2` and FR-036 both say the array is "the geohash-6 of its point **plus all 8 neighbours** = **exactly 10 strings**". **1 + 8 = 9.** A 3×3 block centred on a point is nine cells; there is no tenth, and a probe of `ngeohash@0.6.3` confirms it — `neighbors(centre)` returns 8 distinct cells, none equal to the centre, so the union is 9.

Three options were available and two are worse than saying so:

| Option | Verdict |
| --- | --- |
| **Store 9 (the true 3×3 block)** | **ADOPTED.** Complete coverage, deduped, honest. |
| Pad to 10 with a duplicate | A lie about coverage, and `docs/12` VP-3 requires the array be deduped. |
| Pad to 10 with an arbitrary 10th cell | No extra coverage, and it makes the query match incidents *further* away. |

The practical consequence is nil: **9 ≤ 10**, so the Firestore per-element index limit is satisfied and the coverage requirement is exact. `GEO_CELLS_PER_INCIDENT = 9` and the schema's `.max(10)` deliberately encode two different, both-correct numbers.

### 2.5 The 3×3 block does NOT give zero false negatives above ~74°

`docs/07 §9.2`: "Because every point within 500 m of `P` lies in `P`'s own cell or one of its 8 neighbours, this scheme has **zero false negatives** for the 500 m query."

True below about 74°, and the arithmetic is worth recording because the claim as written is not universal:

```
a geohash-6 cell is ~1.19 km wide in LONGITUDE AT THE EQUATOR, and its
physical width shrinks as cos(latitude). The 3x3 block reaches
1.5 cell-widths from the centre point:

    1.5 x 1.19 km x cos(phi)  >=  0.5 km
    =>  cos(phi) >= 0.28  =>  phi <= 73.7 degrees
```

At 84° N a cell is ~124 m wide, so the block reaches ~187 m, and a point 400 m east is in a different block.

**Consequence for this product: none.** The service is specified for Karachi (17.44 N), and 74° covers Svalbard to the southern tip of Patagonia. The failure mode is a missed *suggestion* — never a wrong coordinate, never a privacy failure, and never a lost report, because nothing in the engine merges.

This is **asserted as a known limitation** in `geohash.test.ts` ("DOES NOT hold above ~74 degrees") rather than left to be discovered, so a future change to precision or block size is a deliberate decision about polar coverage.

### 2.6 Speech-to-text and the duplicate engine are not in this phase

brief §18–§22 asks for a `SpeechToTextService`, which Phase 5 already built as a seam over `docs/09`'s one-pass design. Not re-implemented.

brief §42 correctly excludes dispatch and live tracking, so `responderLocations` and the live map are untouched.

## 3. The nine bugs this phase's own tests found

All in newly written code, documented at the point of the fix.

### 3.1 The category mismatch branch returned `none` instead of `separate_incident`

The most consequential logic bug. Gate 2's early return spread a `base` object whose `decision` was `'none'` and overrode only `reasons`:

```ts
if (!exactCategory && !sameGroup) {
  return { ...base, reasons: ['within_radius', 'category_mismatch'] };  // decision: 'none'
}
```

So **a road accident beside a building fire was filtered out by `findDuplicates` exactly as if it were 3 km away**, and a dispatcher was never told the two were considered and rejected. `docs/07 §9.4`'s worked example and brief §19's example are exactly this case. Now security check #19.

### 3.2 `categoryGroup` read through `Object.prototype`

```ts
CATEGORY_GROUPS['toString']  // → [Function: toString]
```

The "unmapped categories are their own group" fallback never applied to an inherited key, so two unrelated categories compared **equal** — the exact opposite of Gate 2's purpose. Reachable through ordinary data: a category string from AI triage normalisation is arbitrary. Fixed with `Object.hasOwn`. Security check #18.

### 3.3 `ngeohash.decode()` returns `{latitude, longitude}`, not `{lat, lng}`

Typed from the package README rather than probed. The consequence: `const { lat, lng } = decode(cell)` yields two `undefined`s, `clampLatitude(undefined)` returns `0`, and **every geohash cell would have been encoded at the equator** — so no incident would ever match a viewport query. A bare `declare module 'ngeohash';` would have compiled it silently; a real declaration rejects the destructure at compile time. `types/ngeohash.d.ts` now exists and security check #24 asserts its shape.

### 3.4 `decode_bbox` returns a flat 4-tuple, not a pair of pairs

Also typed from the README. `const [sw, ne] = decode_bbox(cell)` destructured a **number**, the `TypeError` was swallowed by a `catch`, and `cellBounds` returned `null` for every input including valid cells. Same root cause as 3.3, same fix.

### 3.5 `neighbours` is the British spelling, which 0.6.3 does not export

`docs/07 §9.2` says "take `ngeohash.neighbours(centre)` if the library exposes it". The exported names are `neighbor` and **`neighbors`**. A probe for the documented spelling returned `undefined`, which is what led to the documented ±0.01° offset approximation.

The exact function is better in three ways (it cannot collapse a neighbour onto the centre near a cell edge, it needs no magic `0.0071` constant, and it makes the spec's "MUST be validated by unit test" requirement moot), so it is the primary path and the offsets are a **fallback** for a version without it. Security check #14.

### 3.6 The Haversine `h` needed a clamp

`Math.asin(1.0000000000000002)` is `NaN`. Without `min(1, h)`, a near-antipodal pair yields a `NaN` distance, and **every downstream comparison is then `false`** — so the pair is neither confirmed nor rejected, silently. Security check #12.

### 3.7 `isValidLatLng` had to reject `NaN` *before* the range test

`NaN > 90` and `NaN < -90` are both `false`, so `if (lat > 90 || lat < -90) reject` **accepts `NaN`** and stores it in Firestore — a document no map can render and no query can filter. Order is asserted by security check #13.

### 3.8 The 120-second duration cap pattern from Phase 5, inverted here

Not a repeat: `use-geolocation.ts` had **zero `useEffect` calls** at one point, so an in-flight `getCurrentPosition` callback could fire into an unmounted hook. Found by the auto-prompt security check reporting "no useEffect found", which is a check failing for an unexpected reason — worth chasing rather than accepting. `mountedRef` added; the effect still never calls `request()`.

### 3.9 A factual error in my own comment

`MANUAL_PIN_MIN_ACCURACY_M` and the geohash header originally claimed RFC 4648 base32 excludes `I`, `L` and `O`. It excludes only `0`, `1`, `8` and `9`; the letters are real symbols. Corrected in place — a "human-friendly alphabet" rationale built on a false claim is worse than the ambiguity it claims to prevent.

## 4. Four bugs in the security checks themselves

This is the project's stated A/B rule paying off, and the failures are of the same kind each time: **a check that finds nothing passes for the wrong reason.**

### 4.1 `functionBodyOf` balanced against a parameter's destructured type

`source.indexOf('{', start)` found the `{` of a *type annotation* rather than the body:

```ts
export async function findDuplicateCandidates(
  point: { lat: number; lng: number },   // ← this brace
```

The walk returned a 28-character fragment, and every scoped check using it silently saw an empty function. A second variant hit a **return type** containing a brace (`Promise<X & { readonly ...: boolean }>`), which ended the walk at the type's `}`. Fixed by skipping the parameter list and detecting a return-type annotation.

### 4.2 Checks matched full signatures, so a signature change broke them silently

`functionBodyOf(source, 'export async function findDuplicateCandidates(...)')` — adding or reformatting a parameter makes `indexOf` return `-1`, which produced a `''` body and reported "not found" rather than failing loudly. Now matched on the function **name**.

### 4.3 A file-wide `.sort()` presence test passed for the wrong function

`.sort()` and `new Set<string>(` appear in `cellsForBounds` and `cellsOverlap` too, so a file-wide test stayed green after `buildGeoCells` was mutated to return an unsorted, undeduped array. Same lesson as 4.1: a check for a property *somewhere* in a file is not a check of the function it belongs to.

### 4.4 The auto-prompt check could not find a `useEffect`

A fixed-shape regex (`useEffect(() => { request()`) did not bite when the call moved one line down, and then reported "no useEffect found" — which turned out to be correct (see 3.8), but only by accident. Now every effect body is extracted by brace matching and required to contain no `request()` call, which is the actual invariant.

A fifth, in the mutation **harness** rather than the checks: it stripped comments with a regex that also dropped **string contents**, so a check looking for `tunableNumber('DUPLICATE_RADIUS_METERS', …)` reported "not found" for a file that plainly contained it, and a mutation appeared to have bitten when the check had never run.

## 5. Distance

`haversineM` is the haversine form, deliberately, and the reason is numerical rather than stylistic:

**The spherical law of cosines loses catastrophic precision for close points.** Two incidents 200 m apart on a 6 371 km sphere have an angular separation of ~3×10⁻⁵ rad, and `acos` of a value within 10⁻¹⁰ of 1 loses most of its significant digits. The haversine form uses `sin²(Δφ/2)`, which stays well-conditioned all the way to zero — which is why identical coordinates return exactly `0` rather than floating-point noise.

**The IUGG mean radius (6 371 008.8 m), not the equatorial one.** The mean minimises maximum error across the globe, so a citizen in Karachi and one in Oslo are equally well served. The choice is stated because the difference is ~0.3%, smaller than any consumer GPS, and a reader should not wonder whether it was deliberate. A test caught my own 111.32-vs-111.195 confusion here — the code was right and the assertion was written against a different constant.

Tested at 0 / 100 / 499 / 500 / 501 / 1000 m as `docs/07 §9.5` requires, at four latitudes, plus the poles, both antimeridian crossings, and an exhaustive grid sweep asserting no pair of valid points yields `NaN`.

`boundingBox` divides the longitude delta by `cos(latitude)`. At 71° N a 500 m circle spans ~0.02° of latitude but only ~0.010° of longitude; using the same delta for both produces a box too narrow in longitude that silently misses candidates at high latitude.

## 6. Duplicate detection

**Radius 500 m, window 6 h**, both env-configurable with `docs/07 §9.5`'s documented ranges enforced by the clamp.

### The candidate query is ONE read

`docs/07 §9.2` is emphatic: *"The implementation MUST use one `array-contains` query on the query point's own geohash-6 and then Haversine-filter. Doing 10 would be a 10x read-cost bug."*

The reasoning is counter-intuitive and worth keeping: because every incident stores its *own* neighbours, a single `array-contains` on the query point's cell already matches every incident in that cell **and** in the 8 surrounding cells, since all of them stored this cell. The stored neighbours are what make one query sufficient.

The exact filter is then applied in code, and it is not optional: a geohash cell is a ~1.2 × 0.6 km **rectangle**, so a matched document's own point can be outside 500 m — the corners of a cell can be 600 m from its centre.

### The gates

| Gate | Rejects when | Decision |
| --- | --- | --- |
| 0 time | `Δt > 360 min`, or a terminal status | `none` |
| 1 distance | `d > radiusM` | `none` |
| 2 category | not exact **and** not same group | **`separate_incident`** |
| 3 text | — | feeds the score |

Gate 2 returning `separate_incident` rather than `none` is the design decision brief §19 asks for. A same-spot, different-category pair is demonstrably two events, and saying so is more useful than a low score — `separate_incident` with `'category_mismatch'` is explainable; `separate_incident` with `'low_overall_similarity'` is not.

### The weights

`0.35·distance + 0.10·time + 0.25·category + 0.30·text`, verbatim, with a `+0.05` nudge for an incident with more than one report.

A test asserts the weights **sum to 1.0**, because `potentialThreshold` is an *absolute* score rather than a percentile — a weight edit that does not renormalise silently changes what 0.55 means. Security check #20 asserts it too.

### The engine never merges

`docs/07 §9.4` rule 1 (FR-041): `confirmed_duplicate` is **a suggestion surfaced to a human**, not an executed merge. The incident is always created.

There is no code path in `lib/duplicates/` or `services/geo/` that merges, deletes, suppresses or de-prioritises. `classifyDuplicate` has no Firestore import (FR-049 requires it), and the service's only Firestore calls are `.get()`. Security check #15 asserts both properties at the source level.

Two Jaccard decisions that matter:

- **Two empty sets return 0, not 1.** `docs/07 §9.5` names the case ("empty text (audio-only) → falls back to category+distance only"). Returning 1 would make an audio-only report and a text report with no distinguishable tokens score as *identical text* and fire the 0.30 weight.
- **The stopword list omits emergency-meaningful words.** "over", "under", "fire", "trapped", "help" are all in it as **absences** deliberately: a standard NLP list contains "over" and "under", and dropping them would destroy the distinction between a fire, a flood and a collapse. A token carrying information about the incident is not a stopword for this product.

## 7. Geolocation

`docs/12 §3.1`'s three options verbatim: `enableHighAccuracy: true`, `timeout: 15_000`, `maximumAge: 30_000`. The override can only **shorten** the timeout.

**No auto-prompt, ever.** `docs/12 §3.5` forbids it and the reason is measurement, not politeness: Chrome remembers a refusal, so a load-time prompt turns "the user said no this once" into "the user can never say yes", and the fallback path becomes the only path for every future session. This is very likely why testing on a phone over a LAN IP produces a permanent denial — the page is not a secure context, the browser reports that as a refusal, and the citizen can never undo it.

Which is why the classifier reports `PERMISSION_DENIED` on an insecure context as **`insecure`**, not `denied`: the user was never asked, and "you denied location access" is a false statement about their own actions.

**One-shot, never `watchPosition`.** A report needs one coordinate; `watchPosition` keeps the GPS chip awake, keeps the location indicator lit, and tracks a citizen for as long as the page is open.

Every non-granted state names a way forward, and `denied` does **not** invite a retry — the browser will not ask again, so "try again" sends the citizen to a settings screen with no explanation.

**A manual pin's accuracy is the zoom-derived radius** (40 px hit target, floored at 30 m), and it is **graded from that declared radius** rather than assumed good. A pin dropped at zoom 3 grades `unknown` and renders the wide dashed ring.

## 8. Privacy

- A `MediaRef`-style bearer URL is never persisted for location; `placeId` is used for a deep link.
- **`route`, `street_number`, `formatted_address` and `postal_code` are never read into a variable** in the geocoder, so the return type has no field a caller could persist. A comment saying "discard these" is a promise; a type with no field is a guarantee.
- The label is prefixed **"Near", never "At"** — in an informal settlement with no official street names, Google returns the nearest *named* entity, which may be 400 m away on a different road.
- An accessible marker name never contains a coordinate. It is read aloud in public.
- `locationText` is set only when the reporter typed it (FR-035), never from a geocode.
- No integrity note and no jump metadata contains a coordinate — they are summaries on a `statusHistory` entry, not a location history.
- The duplicate ring is **not** drawn for a citizen viewing someone else's report, because it reveals that other reports exist in an area.

## 9. What is NOT built

### 9.1 The map rendering layer — `IncidentMap`, `LocationPicker`, markers, popup

**The largest gap, and the one that makes a Phase 6 demo impossible as written.**

Not built: the Google Maps script loader, the `MapPanel`, `useMapInstance`, the marker rendering (advanced or legacy), the click popups, the viewport query subscription, the map controls, and the `MapListFallback`.

**Why**, stated plainly rather than dressed up:

- `MarkerSpec` is built and tested, but it is consumed by nothing. A tested specification with no renderer is a contract, not a feature.
- `docs/12 §7.1` requires an `APIProvider` with a `mapId`, a `NEXT_PUBLIC_MAP_STYLE`, and `AdvancedMarkerElement` with a legacy fallback — roughly a week of work across the loader, both marker paths, the viewport subscription and the fallback UI, none of it verifiable here.
- **No browser was driven during this phase.** There is no DOM renderer in the project and `docs/02 §5` rejects adding one. Untested JSX that cannot be run is the lowest-value code in the repository, and the honest thing is to leave it unwritten rather than to ship a large unverified surface and describe it as a map.
- The `MarkerSpec` work is not wasted: it is the layer that a renderer cannot disagree with, and it is the part whose bugs (a missing shape, a colour-only signal, a coordinate in an accessible name) are the ones `docs/12` actually cares about.

### 9.2 `POST /api/incidents`

Carried forward from Phase 5 §6.1. `attachEvidenceToIncident`, `buildGeoCells` and `checkForDuplicates` are all written and tested; the route that would call them is not. So no incident is created, and therefore no duplicate relationship exists in a database.

### 9.3 Firestore composite index #6

`docs/12 §10.2` specifies `geoCells (array-contains) + status (in) + updatedAt (desc)`. The query in `find-duplicates.ts` uses `geoCells (array-contains) + deletedAt (==) + createdAt (>=) + createdAt (desc)`, with the `status` filter applied after the read. **This needs a deployed index before the endpoint works**, and a missing one surfaces as a Firestore error naming `createdAt` — which the service catches and reports as a named deployment problem rather than a generic 503.

No `firestore.indexes.json` is added, because the exact composite depends on which fields the (unbuilt) create route persists.

### 9.4 Forward geocoding, Places autocomplete, address search

`docs/12 §6` specifies it; brief §32 says to add it "only if already included in the documented architecture and API configuration". It is documented, and `GOOGLE_MAPS_SERVER_KEY` exists, so it is **Phase 7 work** — a separate endpoint with its own rate limit and its own key-restriction story, not part of the location *capture* this phase delivers.

### 9.5 Marker clustering

`docs/12 §9` marks it "P1, flag-gated, and honestly blocked" and documents the un-clustered fallback as what ships in v1. The un-clustered path is what §9.1 would render, so nothing is lost.

### 9.6 Not tested

- **No Firestore read is executed.** `findDuplicateCandidates` is verified by the security check that counts its `array-contains` calls and asserts the exact filter runs after; the query itself needs the deployed index and a seeded collection.
- **`reverseGeocode` makes no real HTTP call.** The component extraction, the cache key, the discard and the copy are all tested; the `fetch` is not.
- **No browser was driven.** Geolocation permission flows, the map, drag-and-drop pin drop, and the `LocationPanel` UI are unexercised.
- **`useLocation`'s state machine** is not tested through React. Its resolution logic is pure and exported, but the hook's transitions are verified by reading rather than by assertion.

## 11. Phase 7 integration points

1. **Map rendering.** `buildMarkerSpec` is the contract. `DEMO_CENTER`/`DEMO_ZOOM` fix "here". `DUPLICATE_RING_TOKENS` and `shouldDrawDuplicateRing(role, isOwn)` fix the ring's treatment and its visibility.
2. **Viewport queries.** `viewportCells(bounds)` returns `{ cells, truncated, spanKm }` with the 25 km span check first and the centred 3×3 clamp; `perCellLimit(n)` gives the per-cell `limit()`. `OPEN_STATUSES` is the status set.
3. **A live map.** `OPEN_STATUSES` includes `resolved` deliberately, so an incident does not vanish from the map the moment a responder arrives.
4. **Duplicate detection at create time.** `checkForDuplicates(report)` returns matches, `nearestM`, `radiusM`, `truncated`, and **`candidatesUnavailable`** — a flag distinguishing "we looked and found nothing" from "we could not look", which brief §37 requires and which a bare `false` would conflate.
5. **Location integrity.** `applyIntegrity(fix, previous, nowMs)` returns the grade to store, the `accuracyM` to store (possibly `null`), the flags, and a coordinate-free note. `impossibleSpeedFrom(fixes)` is the three-point speed check.
6. **Geocoding.** `reverseGeocode(point)` is server-only, never throws, and caches negative results for 60 s against 10 min for positive ones.
7. **Location capture.** `useGeolocation()` for the device and `useLocation()` for the four-way choice, with `LOCATION_FALLBACK_OPTIONS` as the brief §33 trio.

## 12. Honest summary

Phase 6 delivers the **computation and the policy**: distance that is numerically correct at the poles, a geohash scheme with its false-negative limit stated, the `docs/07 §9.4` scoring engine transcribed gate for gate, a one-read candidate query, coordinate validation that actually rejects `NaN`, server-only geocoding with a structural FR-035 discard, and integrity checks that flag and never reject.

It does not deliver **a map**. The rendering layer is unwritten, and until it is, a citizen cannot see a pin or confirm one on a map. The most valuable thing this phase produced is arguably not a feature either: it is the discovery that a correct regex and a documented formula can both be wrong in ways that only a test asserts, and that four of the checks meant to catch exactly that were themselves passing for the wrong reason.
